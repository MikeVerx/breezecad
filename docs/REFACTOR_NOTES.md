## D. Заметки по процессу

### D-01. Mixed line endings
В `Application.cpp` и `Application.h` **смешанные переводы строк**: часть строк CRLF, часть LF. Появлялись из-за патчей, которые вставляли `\n` вместо `\r\n`.

**Решение:** при написании патчей использовать **построчную обработку** с `rstrip('\r')` и явным контролем переводов. Характерный поиск (character-level) с brace-counting для функций.

### D-02. Слипшиеся комментарии в include
При вставке нового include с якорем, включающим хвостовой комментарий, получается слипшаяся строка вида:
#include "a.h" // comment1 // comment2
**Решение:** якорь = только `#include "..."` без комментария. Проверять после каждого патча через `sed -n 'N,Mp'`.

### D-03. Brace-counting работает, но...
Иногда мои скрипты вырезают **только первый if-блок** из цепочки, оставляя осиротевшие следующие. Пример: `if (a) { ... }` + `if (b) { ... }` — если вырезать первый, второй продолжает открывать popup вхолостую.

**Решение:** после вырезания блока — проверять, не остался ли характерный фрагмент второго блока (`BeginPopupModal`, `EndChild` и т.п.).

### D-05. Кириллица в путях ломает Windows-ld
**Симптом:** `ninja` внезапно перестал линковать OCCT (не находит `.dll.a` в `D:/home/Мишаня/occt/...`), хотя `ls` и `cmd.exe dir` файлы видят.

**Причина:** `ld.exe` — нативный Win32-бинарник, использует ANSI CP1251 для путей. MSYS2 передаёт UTF-8 байты, ld их не декодирует.

**Решение:** junction с ASCII-путём:
cmd.exe //c "mklink /J C:\occt D:\home\Мишаня\occt"
cmd.exe //c "mklink /J C:\lunasvg D:\home\Мишаня\lunasvg"
CMakeLists.txt теперь использует `C:/occt/install` и `C:/lunasvg/install`.

**Требуется:** создать junction при первой настройке окружения. Задокументировать в HANDOFF или METHODS.

### D-04. Расширение `Application.h` — риск срыва сигнатур
При замене сигнатуры лямбды-коллбека (`onNotImplemented()` → `onNotImplemented(const char*)`) есть места в коде, где функция вызывается без аргумента — компилятор их не подсвечивает в отрыве.

**Решение:** после смены сигнатуры — `grep` по **всем** местам вызова, не только тем, что помнишь.

## G. Видение MVP (записано 2026-09-26)

**При merge в main — перенести этот раздел в HANDOFF (в раздел «Философия»).**

### Цитата автора (MikeVerx)

> Сейчас надо добиться чистого, стабильного и приятного в работе MVP, который
> не стыдно будет и программистам major показать, и чтобы я и те, кто поставят
> этот САПР получили то, что заявлено — программу с философиями:
>
> - **«Для САПР не всегда нужен ПК с x64-процом за много денег. Хватит простого
>   ноутбука или макбука, начиная с Apple Silicon A18. На нём прога должна
>   хорошо работать, а также минимум места на накопителе»**
>
> - **«Уважение ко времени пользователя»**
>
> - **«Все функции, что остались, по праву можно признать функциями взрослого
>   САПР (т.е. детали, сборки, стандартные изделия и т.п. должны работать
>   стабильно, быть предельно удобными и интуитивными)»**

### Что это значит для кода

| Принцип | Технические следствия |
|---|---|
| **Лёгкость** | Бюджет: 200–500 МБ / старт <1 сек / 4 ГБ ОЗУ / iGPU. Никаких «тяжёлых» зависимостей без нужды. |
| **ARM / Apple Silicon** | Кроссплатформенный CMake, никаких x86-интринсик без `#ifdef`. OCCT уже собирается под ARM. |
| **Уважение ко времени** | Автосейв 1 мин / восстановление после краша за 5 сек / никаких блокирующих модалок / всё отменяется Ctrl+Z. |
| **Взрослый САПР** | Каждая оставшаяся функция — работает **стабильно** и **удобно**. Лучше меньше функций, но каждая — по-взрослому. Лучше не выпустить, чем выпустить криво. |
| **Не стыдно показать** | Код читается за минуты, архитектура слоистая, naming консистентный, нет монолитов >500 строк. Рефакторинг 1.5 не зря. |

### Что это значит для рефакторинга

- **Не гонимся за −100% выноса.** Если остаток (`ui/ribbon/`, `app/`) читается нормально — он может жить в `Application.cpp`. Цель — «5 минут чужому программисту», а не «0 строк в Application».
- **Сомнительные куски** — помечаем, не удаляем. Если при финальной очистке не пригодились — в мусор вместе с операционным мусором.
- **Приоритет — стабильность и удобство**, а не количество вынесенных модулей.

### Что это НЕ значит

- Не значит «делаем всё фичи сразу». Философия — про **качество** того, что делаем, а не про количество.
- Не значит «не выносим крупные модули». `ui/ribbon/` (955 строк) — вынести стоит, потому что он читается как «поток сознания» сейчас. Но если вдруг вынос ломает стабильность — лучше оставить в Application, чем рисковать.

### Практическая цель MVP

Готовый MVP должен:
1. **Запускаться за <1 сек** на среднем железе (Ryzen 5 / M1 / A18).
2. **Работать стабильно** — детали, эскизы, 3D-операции без падений.
3. **Быть удобным** — интуитивным, как Inventor / КОМПАС.
4. **Выглядеть как взрослый САПР** — не «прототип-поделка».
5. **Не съедать ресурсы** — RAM <500 МБ на открытой сборке 200 деталей, FPS 60 idle.

Пока хоть один пункт не выполняется — это не MVP.
