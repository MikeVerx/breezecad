# ADR-0006: Пакеты стандартных изделий (*.bzlib)

- **Status:** Proposed
- **Date:** 2026-10-17
- **Decision makers:** MikeVerx
- **Related:** `src/document/StandardPacks.h/.cpp`, `src/document/StandardParts.cpp`,
  `assets/library/`, [формат для авторов пакетов](../STANDARD_PACKS.md)

## Контекст

Библиотека стандартных изделий (`StandardParts.cpp`) — таблицы `constexpr` и
построение каждого вида кодом на C++. Чтобы добавить стандарт или новый вид
изделия (трубы, профили, листы, уголки, фитинги), нужно править ядро и
пересобирать программу. В окне «Библиотека» с самого начала стоит кнопка
«Добавить пакет стандартных изделий» — заглушка под формат, которого не было.

Нужны:

1. Изделия, которые можно добавлять без программирования и без нового релиза:
   профили и трубы — первыми (под будущий модуль генерации рам).
2. Наравне со встроенными: окно «Библиотека», команды `library.*` (и через них
   MCP), вставка в сборку, обозначение, параметрическое дерево с переменными.
3. Совместимость с тем, что уже есть: ключи стандартов, `Request`, имена
   файлов в папке «Стандартные изделия» (по обозначению).

## Решение

**Пакет — JSON-файл `*.bzlib`: таблицы размеров плюс рецепт построения.**

- **Вид изделия** (`kinds`): папка и разновидность в окне, название, существительное
  для обозначения, внешний вид, материал и **рецепт** — шаги `sketch` (фигуры
  `rect` со скруглёнными углами, `circle`, `polygon`, `hexagon`, `axis`),
  `extrude`, `revolve`. Размеры и координаты — **выражения** над столбцами
  таблицы и длиной `L` («`b/2 - R`»), те же, что понимают поля программы.
- **Стандарт** (`standards`): таблица (`columns` + `rows`) для вида, шаблон
  размера («`{h}×{b}×{t}`») и обозначения, длины — списком (`lengths`) или
  диапазоном (`length`: любая длина от min до max — профиль, отрезанный в
  размер).
- **Построение** — тем же `Builder`, что и встроенные изделия: значения
  столбцов → переменные документа, выражения рецепта → размеры эскизов.
  Деталь — обычное параметрическое дерево, переменные можно менять.
- **Проверка при чтении**: формат и версия, id, имена столбцов (годятся в
  переменные, не `L` и не `d1`…), каждое выражение называет только столбцы и
  `L` и для **каждой** строки таблицы даёт размер больше нуля. Сломанный пакет
  не загружается, пользователь видит причину.
- **Где лежат**: поставляемые — `assets/library/`, пользовательские —
  `<папка настроек>/library/` (кнопка в окне «Библиотека», перетаскивание
  `.bzlib` в окно, команда `library.add_pack`). Пользовательская папка читается
  первой: пакет с тем же id заменяет поставляемую копию.
- **В каталоге библиотеки** виды пакетов получают значения `PartKind` начиная с
  64 (`kFirstPackKind`); остальной API (`Groups`, `StandardsOf`, `Sizes`,
  `Lengths`, `MakePart`, `Designation`…) показывает их рядом со встроенными.
  Новые функции: `FreeLength`, `SizeTitle`. Встроенный крепёж не тронут.
- **Первый пакет** — `gost30245.bzlib`: профили гнутые замкнутые сварные
  квадратные и прямоугольные по ГОСТ 30245-2003 (579 типоразмеров). R — по
  примечанию 2 к таблицам; внутренний радиус r = R − t в стандарте не задан —
  с ним площадь сечения совпадает с массой 1 м по таблицам с точностью до 1 %
  для всех строк (проверено скриптом и тестом).

### Дополнено 2026-10-17

- **Скругления в многоугольнике** (`radii`): острый контур остаётся
  вспомогательными линиями с размерами, дуги касаются сторон и имеют размер
  радиуса — уголки, швеллеры, двутавры строятся параметрически.
- **Вводимые размеры** (`inputs`): ширина листа задаётся в окне, как длина.
- **Имена строк** (`labels`): «10П», «20Б1».
- **Вид из сохранённой детали** (`document`) и **«Моя библиотека»**: деталь
  пользователя с её деревом сохраняется в `<папка настроек>/library/user.bzlib`;
  выбранные переменные — столбцы таблицы, `L` — длина. Удаляется кнопкой в окне.
- **Пакеты по категориям**: профили, трубы, лист, уголки, швеллеры, двутавры —
  каждая таблица сверена с массой 1 м по формуле площади сечения.

## Последствия

**Плюсы**

- Стандарты и простые виды изделий добавляются файлом, без пересборки. Пакеты
  можно держать и в отдельном репозитории (по категориям), формат один.
- Рецепт — данные, а не код: пакет не может выполнить ничего, кроме построения
  эскизов и операций.
- Генератору рам (модуль) хватает того же: сечения — в таблицах пакета.

**Минусы и ограничения**

- Рецепт покрывает «простые» изделия: выдавливание и вращение эскизов из
  простых фигур. Резьба, AutoDrop, подбор аналогов по диаметру остаются у
  встроенного крепежа. Для фитингов, вероятно, понадобятся новые шаги
  (фаска, скругление, массив) — формат расширяется с повышением `version`.
- Изделия пакетов не ставятся в отверстия AutoDrop (`SizeForHole` пуст).
- После загрузки пакетов указатели `StandardInfo*` / `KindInfo` прежние
  недействительны (каталог пересобирается). Окно и команды держат строки-id,
  а не указатели между кадрами.
- Не больше 192 видов из пакетов (`PartKind` — байт).
- Длинные таблицы (сотни размеров) в окне — выпадающий список, без фильтра.

## Альтернативы

1. **Дописывать новые виды в `StandardParts.cpp`.** Быстро для одного вида, но
   каждое изменение данных — правка ядра и релиз; отдельный репозиторий
   библиотеки невозможен.
2. **Модуль, который строит детали через `execute`.** Работает на ABI v1, но у
   модуля нет окна и кнопки, его изделий не видно в «Библиотеке» и при вставке
   в сборку.
3. **Пакет с готовыми деталями `.bzc`.** Дублирование (сотни файлов),
   устаревают при изменении построения, не параметрические по таблице.
4. **Скрипт (Lua, JS) в пакете.** Гибче, но тащит интерпретатор и вопросы
   безопасности чужого кода; для таблиц и простых фигур избыточно.
