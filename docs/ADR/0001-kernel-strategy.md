# ADR-0001: Стратегия геометрического ядра

- **Status:** Accepted
- **Date:** 2026-09-21
- **Decision makers:** MikeVerx
- **Related:** —

## Контекст

BreezeCAD — кросс-платформенный САПР, целевые платформы:

- Windows (включая слабые ПК: 4 ГБ ОЗУ, слабый iGPU)
- macOS (Intel и Apple Silicon)
- Android (планшет + клавиатура + мышь — целевой сценарий мобильной работы)
- ARM везде, где возможно

Проект должен обеспечивать полноценное параметрическое моделирование
(эскизы → операции → сборки), сравнимое с Autodesk Inventor и КОМПАС-3D,
но с существенно меньшим весом и более высокой стабильностью.

Изначально использовался OpenCASCADE (OCCT) напрямую — со всеми модулями:
визуализация (TKV3d, TKOpenGl), OCAF (TKCAF, TKLCAF, TKBin, TKXml),
импортёры/экспортёры (TKDESTEP, TKDESTL, TKIGES и т.д.).

Проблемы текущего подхода:

1. **Вес.** ~108 МБ только OCCT-бинарников в portable-сборке.
2. **Старт.** 2-5 секунд на загрузку десятков DLL даже на среднем CPU.
3. **Память.** 150-250 МБ RSS на простом документе.
4. **ARM/Android.** Официальные сборки OCCT под arm64 неполные,
   кросс-компиляция требует значительных усилий.
5. **Связанность.** Логика документа, сериализации и рендера жёстко
   привязана к OCAF и V3d, что усложняет замену любой из подсистем.

## Рассмотренные варианты

### Вариант A: Оставить OCCT как есть

Плюсы: ничего не меняем, работает.
Минусы: не влезает в целевые ограничения по весу и памяти,
плохо работает на слабых ПК и ARM.

### Вариант B: Написать собственное ядро с нуля

Плюсы: полный контроль, минимальный вес, максимальная скорость.
Минусы: 2-3 года full-time работы одного человека.
Высокий риск не довести до конца. B-Rep — исключительно сложная математика.

### Вариант C: Гибрид — урезанный OCCT за интерфейсом ядра

Плюсы: работает уже сегодня; путь к облегчению без риска;
можно постепенно вытеснять OCCT своими реализациями.
Минусы: абстракция добавляет небольшой оверхед;
нужна дисциплина, чтобы не «протечь» OCCT-спецификой выше интерфейса.

### Вариант D: Использовать другой kernel

- **Manifold** — mesh CSG, не B-Rep, не подходит для параметрического CAD.
- **cadcore** (Rust) — интересен, но незрел, покрытие операций неполное.
- **TGK** (C#) — сознательно ограничен, нет fillet/chamfer/loft.
- Ни один не даёт полного B-Rep-функционала в нужной зрелости.

## Решение

Принят **Вариант C — гибрид**.

Конкретно:

1. **OCCT остаётся** как основа для сложных операций:
   NURBS, fillet, chamfer, loft, sweep, boolean сложных тел,
   импорт/экспорт STEP.

2. **Урезание сборки OCCT.** Исключить из поставки:
   OCAF (TKCAF, TKLCAF, TKBin, TKXml, TKXmlL, TKXmlTObj, TKXmlXCAF),
   IGES (TKDEIGES), OBJ/PLY/GLTF/VRML (TKDEOBJ, TKDEPLY, TKDEGLTF, TKDEVRML),
   Draw, Express, Std, StdL, Helix и любые модули, не используемые напрямую.
   Оставить только: ядро (TKernel, TKMath, TKG2d, TKG3d, TKGeomBase,
   TKBRep, TKPrim, TKTopAlgo, TKBO, TKFillet, TKOffset, TKShHealing, TKMesh),
   импорт/экспорт (TKDESTEP, TKDESTL).
   Ожидаемый результат: ~15-25 МБ DLL, ~50-80 МБ RSS.

3. **Интерфейс `IKernel`.** Вся работа с геометрией идёт через
   абстрактный интерфейс. Ни один модуль выше ядра не знает, что
   под ним OCCT.

4. **Своя документная модель.** Вместо OCAF — собственный формат `.bzc`
   (открытый, документированный) и собственный command stack для Undo/Redo.

5. **Свой рендер.** Вместо V3d/OpenGl OCCT — собственный рендер
   на OpenGL ES 3.0 / Vulkan / Metal / Direct3D 11.
   Цель: единый код для десктопа и мобилок, минимальный оверхед.

6. **Постепенный путь к своему ядру.**
   По мере роста проекта отдельные операции (box, cylinder, extrude
   простых профилей, revolve, примитивы) будут реализованы
   собственными средствами за тем же `IKernel`. OCCT останется
   как «тяжёлый резерв» для STEP и сложной NURBS-математики.

## Последствия

### Положительные

- Работающий продукт уже сейчас, без 2-летнего ожидания.
- Вес приложения реалистично снизить до 200-500 МБ (с учётом ассетов,
  иконок, стандартных изделий, шрифтов).
- Путь к ультра-лёгкой версии (100-150 МБ) без риска для основной.
- Android/ARM становятся реальной целью, а не мечтой.
- Смена ядра в будущем не сломает UI и прикладную логику.

### Отрицательные

- Интерфейс `IKernel` требует дисциплины: OCCT-типы (`TopoDS_Shape`,
  `Handle(...)`) не должны «протекать» выше. Иначе абстракция умрёт.
- Оверхед на трансляции между своим представлением и OCCT-типами.
- Свой рендер — отдельный пласт работы (но это необходимо для
  настоящей кросс-платформенности).
- Свой формат `.bzc` требует написания парсера и сериализатора с нуля.

### Что становится возможным

- **Открытый формат `.bzc`.** Документированный, чтобы сторонние
  проекты (включая молодые CAD) могли читать проекты BreezeCAD.
- **Потенциальный экспорт в STEP с полной параметрикой** (в будущем) —
  чтобы файл можно было открыть в том же Inventor с сохранением дерева
  операций. Не в первой версии, но архитектура к этому готова.

## Границы проекта

**НЕ делаем:**

- FEA/CFD симуляции
- CAM (ЧПУ)
- BIM / архитектура
- Анимация общего назначения
- Полигональное моделирование
- Обратный инжиниринг (mesh → solid)
- Generative design
- Топологическая оптимизация
- Синхронное моделирование (ST-style)
- Облако, коллаборация, файлообмен, PLM
- ECAD-интеграция
- Импорт родных форматов (.ipt, .sldprt, .m3d) — только STEP как обмен
- IGES (устарел)

**Отдельные модули (не в ядре):**

- Сборки
- Стандартные изделия
- Чертежи
- Рендеринг (включая анимации для презентационных сборочек)
- Листовой металл
- Сварные конструкции, трубопроводы, кабели/жгуты

**Отложено на потом:**

- Параметрические таблицы/семейства
- Конфигурации
- Правила (iLogic-подобное)
- Динамика движения сборок (Mate dynamics)
