# ADR-0002: Команды для модулей и MCP-сервер как модуль

- **Status:** Accepted
- **Date:** 2026-10-11
- **Decision makers:** MikeVerx
- **Related:** блок 4 (модули), `src/modules/bz_module.h`, `modules/mcp`

## Контекст

Нужно, чтобы Claude (и любой клиент MCP — Model Context Protocol) мог работать
с деталью в запущенном BreezeCAD: читать дерево и параметры и строить —
эскизы, выдавливание, вращение, правка размеров, экспорт. Подключаться это
должно отдельным модулем, а не частью программы.

ABI модулей v1 этого не позволял:

1. Чтение только сборки (компоненты, габариты); деталей, параметров, дерева нет.
2. ABI задуман только для чтения.
3. У модуля нет входа в главный поток: MCP-серверу нужен свой поток (сеть),
   а документ, ядро и интерфейс — однопоточные.

## Решение

**ABI дополняется, а не ломается.** Новые функции дописаны в конец таблиц
(`abi_version` остаётся 1, наличие проверяется `struct_size`, макрос `BZ_HAS`):

- `BzHostApi.request_main()` — из любого потока: «позови мой `main_tick`»;
  будит главный цикл (`glfwPostEmptyEvent`).
- `BzHostApi.execute(request_json, &reply_json)` — только в главном потоке:
  одна команда над открытыми документами.
- `BzHostApi.config_dir()` — папка настроек, модуль хранит своё в подпапке.
- `BzModuleApi.main_tick()` — хост вызывает в главном потоке между кадрами,
  если кто-то попросил `request_main`.

Модуль v1 (только `init`/`shutdown`) загружается как раньше.

**Команды — JSON, каталог описывает сам хост.** `app/scripting/*`:
`{"command": "part.tree", "args": {…}}` → `{"ok": true, "result": …}` или
`{"ok": false, "error": "…"}`. `commands.list` отдаёт имя, описание и JSON-схему
аргументов каждой команды. Модуль MCP превращает их в инструменты сам — новая
команда в программе появляется в Claude без правки модуля. Один C-вход вместо
десятков C-структур: ABI не растёт с каждой операцией.

**Правки — обычные шаги отмены** через `Session::Execute` (`AddFeature`,
`ReplaceFeature`, `SetVariables`…): пользователь видит их сразу и отменяет Ctrl+Z.
Пока пользователь редактирует эскиз или операцию, изменяющие команды отказывают
с понятным текстом — программа не выдёргивает правку из рук.

**Модуль `mcp`** (`modules/mcp`, собирается в `<bin>/modules/mcp`):
HTTP-сервер на `127.0.0.1` (MCP Streamable HTTP, ответы JSON, без SSE) в своём
потоке; запросы — в очередь, выполняет их `main_tick`. Доступ — по ключу из
`<настройки>/mcp/connection.json`, запросы с заголовком `Origin` (браузер)
отклоняются. Для клиентов, которые запускают сервер как программу (Claude
Desktop), — `bz-mcp-bridge`: stdio ↔ HTTP; без BreezeCAD отвечает сам
(«запустите BreezeCAD»).

**Согласие пользователя.** Новое поле манифеста `enabledByDefault: false`:
модуль, открывающий порт, выключен, пока пользователь не включит его в
«Настройки → Модули» (выбор запоминается в `modules.json`, ключ `on`).

## Следствия

Плюсы:
- Любой модуль (не только MCP) может читать и менять документ тем же путём.
- Список команд и их описания живут в одном месте — в программе.
- Модуль MCP не линкуется с библиотеками BreezeCAD: только C-ABI.

Минусы и ограничения:
- Метка падения ставится на весь `main_tick`: если упадёт ядро внутри команды
  модуля, выключат модуль (как и для любого кода внутри вызова модуля).
- Модуль может записывать файлы по путям клиента (`doc.save`, `doc.export`) —
  как «Сохранить как»; защита — ключ и только локальный адрес.
- Долгое перестроение держит ответ (ожидание до 3 минут, потом ошибка).

## Рассмотренные варианты

- **C-структуры на каждую операцию в ABI** — ABI растёт и ломается с каждой
  новой операцией; отвергнуто.
- **Отдельная программа без окна над файлами .bzc** — проще, но не видит
  открытое у пользователя и не даёт смотреть, как строится деталь; отвергнуто.
- **Только HTTP, Claude Desktop через `npx mcp-remote`** — нужен Node.js у
  пользователя; мост на C++ — один файл без зависимостей.
