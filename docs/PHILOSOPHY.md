## 1. Миссия

**BreezeCAD — это САПР для обычных людей на обычном железе.**

Не для корпораций с бюджетом на лицензии Inventor. Не для тех, у кого
RTX 4080 и 128 ГБ ОЗУ. А для:

- **Школьника**, которому от старшего брата достался хилый ПК, но который
  мечтает освоить инженерное 3D и печатать пластиковые изделия.
- **Студента**, который не купит игровой ноут за 1000+ долларов.
- **Человека старшего поколения**, у которого на старом железе возникла
  потребность создать что-то самостоятельно.
- **Владельца Mac**, которому крупные CAD-компании не считают нужным
  сделать нормальный продукт под Apple Silicon.

**Это личный проект.** Он пишется автором для себя и своего окружения.
Он попадёт в интернет только когда автор будет удовлетворён тем, что есть.
Не раньше.

## 2. Три философии

### 2.1. Лёгкость

> «Для САПР не всегда нужен ПК с x64-процом за много денег. Хватит простого
> ноутбука или макбука, начиная с Apple Silicon A18. На нём прога должна
> хорошо работать, а также минимум места на накопителе.»

**Технически:**
- Бюджет: **200–500 МБ установки, старт <1 сек, 4 ГБ ОЗУ, iGPU**.
- **ARM / Apple Silicon — не «в будущем», а приоритет.**
  Apple открыл ворота в ARM-эру. Nvidia, Intel, AMD уже выкатывают свои
  варианты. Через 2–5 лет ARM станет новым витком рынка — и мы должны
  быть в первой волне, а не догонять.
- Никаких тяжёлых зависимостей без нужды. Каждая — с обоснованием в ADR.

### 2.2. Уважение ко времени пользователя

> «Уважение ко времени пользователя.»

**Технически:**
- Автосейв — раз в минуту, 3 версии, atomic write.
- Восстановление после краша — за 5 секунд, без модальных «а вы точно?».
- Ноль телеметрии без согласия.
- Всё отменяется: Ctrl+Z, Esc.
- Прогресс-бары для всего, что >1 сек («сглаживание: 18/84»).
- Никаких модалок, которые нельзя закрыть.
- При тяжёлых операциях — сначала **примитив-макет**, потом одна операция
  финального расчёта. Пользователь выбирает что хочет → видит прогресс →
  получает результат.

### 2.3. Взрослый САПР

> «Все функции, что остались, по праву можно признать функциями взрослого
> САПР (т.е. детали, сборки, стандартные изделия и т.п. должны работать
> стабильно, быть предельно удобными и интуитивными).»

**Технически:**
- **Лучше 5 операций идеально, чем 50 криво.**
- **Лучше не выпустить, чем выпустить криво.**
- Функция «сделана», только если:
  - работает стабильно (нет случайных падений);
  - удобна (интуитивна как Inventor / КОМПАС);
  - предсказуема (одинаковый результат всегда).

**Антипример:** FreeCAD. Смотреть страшно, баги не фиксят годами.
Мы так не делаем.

## 3. Открытый формат как миссия

> «Я хочу, чтобы мой формат мог стать английским (в контексте международного
> языка) в мире САПР. Чтобы любая компания, которая не настолько узколоба,
> чтобы отказаться от значительного куска рынка, могла свободно читать
> модели, созданные в моём ПО, открывать деревья изменений.»

**Это финальная позиция.** Формат `.bzc` документируется как
**открытый стандарт**, чтобы:
- Сторонние CAD могли читать наши файлы.
- Дерево операций было переносимо.
- Инженеры не страдали от искусственных ограничений.

**Односторонняя совместимость:** мы можем не читать чужие форматы,
но наши файлы — открыты для всех.

**Почему:** пора закопать топор недружелюбия. Люди должны объединяться
в общем деле — быть инженерами и создавать крутые штуки.

**Что это значит для кода:**
- `FILE_FORMAT.md` — публичный, версионируется, миграции обязательны.
- Формат `.bzc` не привязан к OCCT, к BreezeCAD, к чему-либо ещё.
- Схема ZIP + JSON + бинарные части — понятная сторонним парсерам.

## 4. Принципы разработки

### 4.1. Минимум зависимостей, максимум контроля

- Каждая зависимость — обоснование в ADR.
- Если можно написать 200 строк самим вместо 20 000 чужого кода — пишем.
- OCCT — временный «тяжёлый резерв» (ADR-0001). Цель — своё ядро.
- OCAF — временный мост. Цель — свой `.bzc`.

### 4.2. Борьба за байт как дисциплина

- Аллокация в hot-path — баг.
- `std::function` в кадре — баг.
- Хардкод-цвет в UI — баг (RULES п.30).
- `static` в функции — баг (RULES п.20).

**Принцип:** мы ведём себя как программисты 80-х, которые воевали за
каждый килобайт. Только у нас не 640 КБ, а 4 ГБ — принцип тот же.

### 4.3. Код — для чужого программиста

- Понять проект за 5 минут (RULES п.21).
- Никаких монолитов >500 строк.
- Слои с чёткими границами.
- Единый стиль, консистентное именование.
- README, ARCHITECTURE, CONTRIBUTING — обязательны.

### 4.4. Уважение к чужим решениям

- «Мёртвый» код может быть debug-helper (B-12) или заготовкой (C-01).
- Не удаляем без явного согласования (REVIEW-правило в RULES).
- Не «улучшаем» канон по ходу — сначала обсуждаем.

### 4.5. Честность с собой и с пользователем

- Компромиссы документируем, а не прячем.
- Ошибки признаём («моя вина»).
- Не «докручиваем» сломанное — откатываем.

## 5. Что НЕ делаем

**Отвергнутые области:**
- FEA/CFD, CAM, BIM, облако, PLM, ECAD.
- Обратный инжиниринг (mesh → solid).
- Generative design, топологическая оптимизация.
- Синхронное моделирование (ST-style).
- Импорт `.ipt`, `.sldprt`, `.m3d` (только STEP).
- IGES (устарел).

**Почему:** каждая из этих областей — годы работы. Мы **не хотим быть «всем»**,
мы хотим быть **лучшими** в узкой нише: параметрическое моделирование
деталей и сборок для одного пользователя на слабом железе.

**Что говорит автор:**

> «Не претендую на нишу крупных САПР. Те, у кого есть деньги — купят
> себе лицензию крупного ПО, поставят роскошные компы и будут работать.
> Моя история — про обычных людей, которые носятся с кряками или
> нарываются на неоправданные ограничения. Просто потому что ААА-компании
> решили воткнуть в свои продукты всё и сразу.»

## 6. Бюджет производительности

**Формальные метрики, которые проверяем на каждом релизе:**

| Параметр | Цель |
|---|---|
| Старт | <1 сек |
| Деталь (100 фич) | RAM <100 МБ |
| Сборка (200 деталей) | RAM <500 МБ |
| FPS в 3D idle | 60 |
| **FPS в 3D с деталью 1000 фич** | **≥35** (нижняя планка) |
| Установка | 200–500 МБ |

**Если хоть один пункт не выполняется — релиз не выходит.**

Автор на вопрос про FPS:
> «Не менее 35 FPS, как я думаю. Но тебе я доверяю.»

**Android UX:** единый UI, оптимизированный под сенсорные экраны,
с поддержкой пера, мыши и клавиатуры. Не два разных UI.

## 8. План проверки философии

### 8.1. Симуляция слабого железа

Не угадывать минимальные требования — **измерять физически**:

- **CPU:** `powercfg` throttling, BES (Battle Encoder Shirase).
- **RAM:** Windows Job Objects с лимитом памяти.
- **GPU:** `LIBGL_ALWAYS_SOFTWARE=1` (Mesa) — software rendering.
- **ARM:** `qemu-user-static` — эмуляция ARM на x86.

**Цель:** нащупать физические пределы искусственно. Если работает на
симулированном Ryzen 3 + 4 ГБ — работает на реальном.

### 8.2. План оптимизаций

**Сейчас (до Фазы 2):**
- LTO (Link Time Optimization) для Release.
- `strip` бинарника.
- `--gc-sections` (мёртвый код).
- Ribbon cache (пересчёт layout по событию, а не каждый кадр).
- Object pool для AIS_Shape (если OCCT позволит — с проверкой стабильности).

**Фазы 2-3:**
- Асинхронная тесселяция (прогресс-бар, UI не блокируется).
- Progressive autosave с backpressure (подстраивается под скорость диска).

**Фаза 8:**
- Свой рендер (без TKV3d/TKOpenGl).
- GPU instancing для сетки эскиза.
- «Микроволновка»-режим (минимальная тема, reduced FPS превью).

**Не берём:**
- Lazy icons (иконки остаются как есть, векторные).
- Отдельную «урезанную» тему без иконок.

## 9. Что это значит для ассистента (новый чат)

Когда читаешь этот файл, помни:

1. **Мы воюем за байт.** Каждая аллокация — с обоснованием.
2. **Мы не гонимся за фичами.** Лучше меньше — но идеально.
3. **Мы уважаем пользователя.** Автосейв, undo, никаких модалок.
4. **Мы документируем компромиссы.** Не прячем, а объясняем.
5. **Мы работаем по RULES.** 38 правил — не бумажка, а дисциплина.
6. **Производительность > удобство > функционал.**
7. **MVP может застыть.** «Пусть проект застрянет на этапе полностью
   рабочего MVP, но оно будет работать и будет удобным».

**И самое важное:** мы делаем это вместе, годами, с удовольствием.
Проект — не «работа», а творчество. Так к нему и относимся.
