# BreezeCAD — Правила работы

**Единый источник правды о том, как устроена работа над проектом.**
Обновляется при изменении договорённостей. Читается первым делом в новом чате.

---

## 1. Работа с пользователем (MikeVerx)

1. **ТОЛЬКО консольные команды.** Никогда не просить «открой редактор»,
   «найди строку глазами», «открой nano». Любая правка файла = одна или
   несколько команд в терминале.

2. **После каждой правки — команда проверки.** `grep -a -n`, `diff`, `head`,
   `tail`, `hexdump` — что уместно. Пользователь должен видеть результат.

3. **Всегда добавлять команду запуска для проверки.** Если правим код —
   давать команду сборки (`ninja`) и запуска (`./run.sh`).

4. **НИКОГДА не предлагать ребут системы.** Даже если кажется, что драйвер
   завис — искать решение без перезагрузки.

5. **Правки файлов — через Python heredoc.** Использовать
   `python << 'PYEOF' ... PYEOF`, не `sed -i`.
   - `sed -i` ломает CRLF (переписывает Unix-переводами), git показывает
     весь файл как изменённый.
   - Python открывает файлы с `encoding='utf-8', newline=''`.
   - Для замены больших функций — поиск по границам (`find` start/end
     индексов), а не regex.

6. **`grep` — всегда с `-a`.** Файлы с кириллицей в комментариях grep считает
   бинарными; без `-a` он не ищет в них.

7. **Кириллица в Python — только в heredoc.** `python -c "..."` с кириллицей
   падает (`bytes can only contain ASCII`).

8. **Коммит после каждой рабочей порции.**
   Формат: `<тип>(<область>): <краткое описание>` + пустая строка + детали.
   Типы: `feat`, `fix`, `refactor`, `docs`, `build`, `chore`, `assets`, `wip`.
   После коммита — всегда `git push`.

9. **НИКОГДА не коммитить секреты.** Если пользователь случайно скинул
   токен/пароль/ключ — сразу сказать «отзови, скомпрометирован».

10. **Структура в ответах.** Длинные ответы — секции, таблицы, списки.
    Не бояться подробности, если вопрос требует деталей.

11. **Признавать ошибки честно.** Если патч упал, гипотеза не подтвердилась,
    пользователь нашёл проблему — сказать «моя вина», объяснить почему,
    предложить решение. Не защищаться, не «докручивать» сломанное.

12. **Если сборка упала — немедленно откатывать.**
    `git checkout -- <файл>` или `mv file.bak file`, потом думать.
    Не чинить поверх сломанного.

13. **Не гадать — спрашивать.** Лучше 3 уточняющих вопроса, чем 30 минут
    работы не в ту сторону.

14. **Быть тёплым.** Пользователь работает много часов. Радоваться победам,
    поддерживать в неудачах, шутить иногда. Но работа важнее флирта.

## 2. Работа с кодом

15. **Правило «одно облачко».** Каждая команда для копипаста = отдельный
    блок ```bash ... ```. Не смешивать несколько операций в один блок,
    если между ними нужна проверка.

16. **Топология — святое.** Кнопки не обрезаются, иконки не мелкие, правая
    панель не «жирная». Чек-лист топологии в UI_LAYOUT.md (раздел 2.3).

17. **Никаких Unicode box-drawing в heredoc.** Символы `┌─┬─┐` теряются
    при вставке в терминал. Использовать только `+`, `-`, `|`.

18. **Не использовать `..` в UI.** Шрифт Inter не содержит многоточия в
    кириллических глифах — рендерится как `?`. Вместо обрезки — уменьшать
    шрифт до победного, потом сокращать подпись.

19. **Одна функция — одно место.** Не дублировать логику. Если что-то
    делается в двух местах — вынести в helper.

20. **Никаких `static` переменных в member-функциях для состояния между
    вызовами.** Использовать member-поля класса (иначе разные функции
    «не видят» друг друга).

## 3. Архитектура и качество кода

21. **Код должен быть приятным для чужого программиста.**
    Критерий: если опытный C++-разработчик откроет проект впервые — он
    должен понять за 5 минут, куда идти, и не поморщиться.

    Следствия:
    - Слои: `platform` / `kernel` / `doc` / `app` / `ui`.
    - Никаких монолитов >500 строк (Application.cpp = рефакторить в Фазе 1.5).
    - Единый стиль (clang-format).
    - README с описанием архитектуры.
    - CONTRIBUTING.md для желающих помочь.

22. **Разделение ядра и UI.** UI не должен знать про OCCT. Ядро не должно
    знать про ImGui. Между ними — интерфейс `IKernel`.

23. **Никаких хардкодов путей.** `std::filesystem` или glfw-хелперы.

24. **Платформенное — под `#ifdef`.** Только там, где действительно нужно.

25. **Тесты — для ядра.** UI тестами не покрываем (слишком дорого).
    Ядро: геометрия, парсинг, миграции — да.

---

## 4. UI/UX-принципы

26. **Уважение ко времени пользователя.**
    - Автосохранение раз в минуту (3 версии, atomic write).
    - Никаких модальных окон, которые нельзя закрыть.
    - Всё можно отменить (Ctrl+Z, Esc).
    - Прогресс-бары для всего, что >1 сек.
    - Восстановление после краша — за 5 секунд.

27. **Языки.** Сейчас — русский (скорость разработки). Языковые пакеты
    расширим, когда закроем MVP. Архитектура локализации — уже готова
    (Localization.cpp), добавить новые языки = дописать словарь.

28. **Ноль телеметрии без согласия.** Никаких «отправить отчёт в Microsoft».

29. **Дизайн — Inventor + КОМПАС.** Структура от Inventor, частично
    от КОМПАС. Взаимодействие клава-мышь — от КОМПАС.

30. **Всё окрашивается от темы.** Никаких хардкод-цветов в UI-коде.

---

## 5. Документация

31. **Любое решение — в ADR.** Architecture Decision Record в `docs/ADR/`.
    Формат: контекст / решение / следствия.

32. **Любая проблема — в TECH_DEBT.** С ID, статусом, описанием, планом.

33. **Любой UI-баг — в UI_ISSUES.**

34. **Изменения — в CHANGELOG_WORK (по фазам).** С датой, коммитами,
    сделанным, проверкой, открытыми вопросами.

35. **Что сработало и что нет — в METHODS.** Самый ценный документ для
    будущих сессий.

---

## 6. Процесс при переполнении контекста

36. **Перед переходом в новый чат** — скинуть пользователю `docs/HANDOFF.md`
    (или ссылку). Он передаст его в новый чат.

37. **В новом чате** — ассистент первым делом читает HANDOFF, потом
    PROJECT_STATE, CANON_FEATURES, ROADMAP, TECH_DEBT. Только потом
    берётся за работу.

38. **Контрольные вопросы для самопроверки** — в HANDOFF (раздел «Проверь,
    что ты понял»). Ассистент отвечает на них перед началом работы.
