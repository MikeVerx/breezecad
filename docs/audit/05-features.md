# Предложения функций и модулей

Отправная точка — ваша аудитория: **DIY, 3D-печать и ЧПУ**. Предложения
отсортированы по соотношению «польза для этой аудитории / цена», и для каждого
сказано, на что в коде оно опирается уже сейчас. Номера **F-xx** постоянные.

Обозначения цены: **S** — дни, **M** — 1–2 недели, **L** — месяц и больше.

---

## 1. Чертежи (то, что вы запланировали после первой стабильной альфы)

Хорошая новость: основа уже в сборке. `TKHLR` (удаление невидимых линий в
OCCT) **уже подключён** в `cmake/OpenCascade.cmake` для вьюпорта.

### Предлагаемый объём первой версии (MVP)

| Шаг | Что | Опора в OCCT/коде | Цена |
|---|---|---|---|
| 1 | Лист формата А4–А0 с рамкой и основной надписью (ГОСТ 2.104, форма 1) — шаблон в JSON | — | S |
| 2 | Основные виды (спереди/сверху/слева) и изометрия по детали, масштаб листа | `HLRBRep_PolyAlgo` (быстро, по сетке) для предпросмотра, `HLRBRep_Algo` (точно) для печати | M |
| 3 | Видимые/невидимые линии разными типами, осевые линии отверстий и тел вращения | данные для осей уже есть: `FaceReference.curved`, `Hole`, `Revolve` | S |
| 4 | Разрез по плоскости со штриховкой | `Section` уже есть для модели | M |
| 5 | Размеры: линейный, диаметр, радиус, угол — **ассоциативные** (по рёбрам вида, обновляются при изменении детали) | механизм ссылок `EdgeReference` уже решает «найти ребро после перестроения» | M |
| 6 | Экспорт в PDF и DXF (для лазерной резки DXF — главное) | PDF — через свой простой вывод векторов; DXF — текстовый формат, писать самим | S |

**Совет по архитектуре:** чертёж — отдельный тип документа (`.bzd`), который
ссылается на деталь по пути, как сборка на детали (`DocumentTypes` уже есть).
Вид чертежа хранит только направление, масштаб и положение; линии всегда
считаются из детали. Тогда изменение детали автоматически обновляет чертёж.

**Позже:** выносные элементы, виды по стрелке, таблица отверстий, спецификация
сборки (данные уже есть: `designation`, `material`, количество в `ComponentRecord`).

## 5. Модули (модульная архитектура уже есть)

Механизм модулей (`modules/bz_module.h`, проверка требований к железу,
отключение упавшего) хорош — ему не хватает «чем модуль может заниматься».
Сейчас модуль только читает сборку. Предложения по расширению C-ABI, по порядку:

1. **Команда на ленте**: модуль регистрирует кнопку и получает вызов.
2. **Генератор операции**: модуль получает параметры из простой формы
   (числа/выбор) и возвращает эскиз или тело → так делаются F-08 и F-09 силами
   сообщества.
3. **Экспорт/импорт формата**: модуль получает треугольники или контуры → DXF,
   SVG, OBJ без правки ядра.
4. **Анализ**: модуль получает грани с нормалями и площадями и возвращает
   раскраску → F-04, F-05 как модули.

Модули стоит запускать в отдельном процессе (см. [02-isolation.md](02-isolation.md),
ступень 3) — тогда чужой модуль никогда не уронит программу.

## Что предложил бы делать первым после стабилизации

1. F-01 + F-02 + F-03 — за неделю закрывают три самые частые боли печатников.
2. F-07 + F-10 — экспорт под реальные станки, по паре дней.
3. Чертежи по плану из раздела 1.
4. F-14 — открывает доработку чужих моделей, это сильно расширит аудиторию.
