## Критичные (К)

### B-01 — Повреждённый или «чужой» файл роняет программу при открытии ✅ — **исправлено (ccf2412)**

**Что видит пользователь:** открывает `.bzc`, присланный товарищем или
отредактированный вручную, — программа исчезает без сообщения.

**Причина:** загрузчик JSON (`nlohmann::json`) бросает исключение `type_error`,
если поле есть, но другого типа (`"name": 5` вместо строки). Функции
`.value(…)`, `.get<…>()` бросают, а не возвращают ошибку. Выше по стеку
(`Workspace::LoadSession`) исключение никто не ловит → `std::terminate`.

**Где:** `src/document/BzcFile.cpp` — `DocumentFromJson`, `ReadBzcArchive`
(`manifest.value(...)`); `src/document/SketchFeature.cpp` — `j.value("type", "")`;
`src/assembly/AssemblyFile.cpp` — `AssemblyFromJson`; вызов из `src/app/Workspace.cpp:64`.

**Стенд (ASan):** из 9 испорченных файлов 6 бросают исключение, которое в
программе = вылет: `part.name` числом, `units` строкой, операция числом,
`type` числом, `nextId` строкой, тип кривой числом.

**В программе:** `breezecad broken.bzc` (в копии `кронштейн.bzc` имя детали
заменено числом) → SIGABRT, в логе
`Crash: uncaught exception: [json.exception.type_error.302] type must be string, but is number (last action: open: broken.bzc)`.

**Исправление:** обернуть `DocumentFromJson`, `AssemblyFromJson` и чтение
манифеста в `try { … } catch (const nlohmann::json::exception&) { return Error{"Файл повреждён: …"}; }`.
Одно место на каждый загрузчик, 10 строк. Плюс тест с этими 9 файлами.

### B-02 — Дуга или эллипс со ссылкой на несуществующую точку: запись мимо памяти ✅

**Что видит пользователь:** вылет при открытии файла или при перестроении;
в худшем случае — тихая порча памяти и «странные» вылеты позже.

**Причина:** конструктор `EquationSystem` для каждой дуги и эллипса добавляет
уравнения с индексами точек, не проверяя, нашлась ли точка (`PointIndex` вернёт
`-1`). Дальше `Residual`/`Jacobian` читают `x[-1]` → чтение за пределами массива.
Загрузчик эскиза не проверяет, что линии/дуги/связи ссылаются на существующие
точки.

**Где:** `src/sketch/EquationSystem.cpp:98-113`; `src/document/SketchFeature.cpp:154-245`.

**Стенд (ASan):** `heap-buffer-overflow` для дуги и для эллипса с «висячими»
точками. Отрезок и сплайн с такими же ссылками — не падают (там проверки есть).

**Исправление:**
1. В конструкторе пропускать дугу/эллипс, если любой индекс < 0.
2. После загрузки — один проход «санитар эскиза»: выбросить кривые и связи с
   висячими ссылками и дубли id, сказать об этом в `LoadReport.warnings`.

### B-03 — Угловой размер с большим числом вешает программу навсегда ✅ — **исправлено (be6e0cb)**

**Что видит пользователь:** вводит в угол «100000000» (залипла клавиша) или
выражение, дающее большое число, — окно перестаёт отвечать. Только снять
процесс; несохранённое — потеряно (кроме автосохранения).

**Причина:** `WrapAngle` приводит угол к (−π; π] циклом «вычитать 2π, пока
больше π». Для 10¹⁵° это квадриллионы итераций, а для ещё больших чисел
`a - 2π == a` — цикл вечный. И вызывается он на каждом вычислении невязки, то
есть тысячи раз за решение.

**Где:** `src/sketch/EquationSystem.cpp:17-21`; тот же приём в
`src/sketch/Trim.cpp:13-17`.

**Стенд:** угол 10⁶° — 2 мс; 10⁹° — **1,0 с**; 10¹⁵° — не закончилось за 5 с
(снято по таймеру).

**Исправление:** `std::remainder(a, 2π)` — одна строка, работает за постоянное
время. Заодно ограничить угловые параметры разумным диапазоном при вводе.

### B-04 — Открытие файла при «потерянном» открытом документе — вылет ✅ — **исправлено (21d934f)**

**Сценарий:** открыта сохранённая деталь `A.bzc`. Её удалили, переименовали в
Проводнике или она лежала на флешке, которую вынули. Пользователь открывает
**любой другой** файл (в т. ч. из «Недавних») → вылет.

**Причина:** `std::filesystem::equivalent(a, b)` без `error_code` бросает
исключение, если хотя бы одного файла нет. Проверено на той же libstdc++, что в
MinGW: `filesystem error: cannot check file equivalence: No such file or directory`.

**В программе:** открыты `C.bzc` и `B.bzc`, файл `C.bzc` удалён, на главной
странице щелчок по «B» в «Недавних» → вылет:
`filesystem error: cannot check file equivalence: No such file or directory [/tmp/C.bzc] [/tmp/B.bzc]`.
Падает даже при щелчке по **уже открытому** документу.

**Где:** `src/app/Workspace.cpp:90`; `src/app/assembly/AssemblyUi.cpp:421`
(вставка детали в сборку, которую переместили).

**Исправление:** перегрузка с `std::error_code` (при ошибке считать «не тот
же файл»). Две строки.

### B-05 — Переключение вкладки при открытой операции: «Отмена» удаляет операцию в чужом документе ✅

**Сценарий:** две открытые детали. В первой начато «Выдавливание» (панель
открыта, операция уже стоит в дереве как предпросмотр). Щелчок по вкладке
второй детали. Затем Esc / «Отмена» / «Готово».

**Причина:** редакторы операций (`app.ops`) и редактор эскиза — **одни на всё
приложение**, а не на документ. Щелчок по вкладке (`Bars.cpp:50`) вызывает
только `Workspace::Activate`, не закрывая редактор (закрытие и открытие
документа его закрывают — `EndEditing`, а переключение — нет). Дальше
`Cancel` выполняет `session.doc.Take(myFeature)` уже для **второго** документа.
Идентификаторы операций — порядковые номера внутри документа, у двух деталей
они совпадают сплошь и рядом. Итог:
- во второй детали удаляется (или подменяется) **посторонняя** операция с тем же
  номером — и это не попадает в историю отмены;
- в первой детали остаётся «висячий» предпросмотр, который сохранится в файл.

**Воспроизведено в программе** (Xvfb, снимки экрана):
1. Открыты `B.bzc` (кронштейн, «Выдавливание1» = id 26) и `A.bzc` (только
   «Эскиз1», следующий id = 26).
2. В A — «Выдавливание», панель открыта (новая операция получила id 26).
3. Щелчок по вкладке B → панель выдавливания **осталась** и уже правит
   «Выдавливание1» детали B (показывает 10 мм вместо 15, деталь B перестроилась).
4. «Отмена» → в детали B **пропало «Выдавливание1»** (основание пластины), документ
   B не помечен изменённым, кнопка «Отменить» неактивна.
5. В детали A «отменённое» выдавливание **осталось** в дереве как обычная операция,
   тоже вне истории отмены.

**Где:** `src/app/shell/Bars.cpp:50`, `src/app/features/FeatureOperationEditor.cpp:118-126`,
`src/app/features/OperationEditors.h`.

**Исправление:** при смене активной вкладки вызывать `EndEditing(app)` (как при
открытии/закрытии). Надёжнее — хранить в редакторе указатель на `Session`, с
которой он начал, и проверять его в каждом `DrawPanel/Done/Cancel`.

### B-07 — `FaultGuard` оставляет «мину» после перехваченного падения OCCT 📖 — нужно решение

**Как сейчас:** при аппаратном сбое внутри операции (обращение по плохому
адресу) `RunGuarded` прыгает назад через `siglongjmp`/`__builtin_longjmp`,
минуя деструкторы всего, что было на стеке.

**Почему это опасно** (проверено по исходникам OCCT 7.8.1):
- OCCT сам ставит «ловушки» `OCC_CATCH_SIGNALS` почти во всех алгоритмах
  (булевы, скругления, сетка — 20+ модулей). Каждая ловушка — объект
  `Standard_ErrorHandler` на стеке, вставленный в **общий на весь процесс**
  список `Top` под мьютексом (`Standard_ErrorHandler.cxx`). Прыжок мимо
  деструктора оставляет в списке указатель на уже несуществующий кусок стека.
- `OCC_CONVERT_SIGNALS` включён для **всех не-MSVC сборок**, то есть и для
  Linux, и для вашей Windows-сборки MinGW (`adm/cmake/occt_defs_flags.cmake:35`).
- Если сбой случился, пока был захвачен мьютекс OCCT (`Standard_Mutex::Sentry`
  снимает его как раз через этот список), мьютекс остаётся захваченным
  навсегда → **следующая** операция зависает.

**Итог:** одна «спасённая» операция может превратиться в вылет или зависание
через минуту, на совершенно невинном действии — и такой отчёт уже не связать с
причиной.

**Варианты (решение за вами):**
1. **Родной механизм OCCT**: `OSD::SetSignal(false)` при старте +
   `OCC_CATCH_SIGNALS` внутри наших `try`. Тогда сбой превращается в обычное
   исключение `Standard_Failure` с правильной раскруткой списка. Дёшево (десятки
   строк), но надо проверить на Windows/MinGW, как он уживается с нашим
   `SetUnhandledExceptionFilter` в `main.cpp`.
2. **Отдельный процесс для геометрии** — настоящая изоляция, см.
   [02-isolation.md](02-isolation.md), «Ступень 3». Дорого, но закрывает и
   B-08, и B-09, и B-22 разом.
3. В любом варианте после перехваченного сбоя — сразу аварийное
   автосохранение и плашка «ядро сбоило: сохраните работу и перезапустите
   программу».

Рекомендация: 1 + 3 сейчас, 2 — после первой стабильной альфы.

### B-08 — Падение в рабочем потоке OCCT не перехватывается вовсе 📖 — нужно решение

`SetUpOcct()` включает `BOPAlgo_Options::SetParallelMode(true)` — булевы
операции идут на нескольких потоках пула OCCT. `FaultGuard` защищает только
поток, вызвавший `RunGuarded` (`thread_local tlLanding`). Сбой в рабочем потоке
→ `OnFault` видит «не наш» → обычный вылет. А сбои в OCCT чаще всего как раз в
пересечениях, то есть в параллельной части.

**Где:** `src/kernel/Model.cpp:746-756`, `src/core/FaultGuard.cpp`.

**Решение:** вариант 1 из B-07 закрывает и это — пул OCCT
(`OSD_ThreadPool.cxx:285`) сам ставит `OCC_CATCH_SIGNALS` в каждом потоке и
передаёт ошибку вызвавшему. Без него: временно `SetParallelMode(false)` (на
2 ядрах i5-4200U потеря скорости небольшая).

### B-09 — Закрытие во время долгого фонового перестроения: вечное ожидание 📖

`Session::~Session` делает `thread.join()`. Перестроение в фоне отменить нельзя.
В HANDOFF сказано, что `UnifySameDomain` на резьбе «висит минутами» — в такой
момент закрытие вкладки или выход «замораживают» окно, ОС предлагает снять
задачу → потеря несохранённого в других вкладках.

**Где:** `src/app/Session.cpp:41-43`, `57-76`.

**Исправление:**
1. Флаг отмены (`std::atomic<bool> cancel`), проверяемый между операциями в
   `RebuildSlice`, и `Message_ProgressRange` с `UserBreak()` в долгих алгоритмах
   OCCT (булевы, скругления, сетка его поддерживают).
2. При выходе: если фон не закончился за ~1 с — показать «Завершаю
   перестроение… [Выйти без ожидания]», а «без ожидания» = `detach` + `quick_exit`
   после сохранения настроек.

### B-10 — Переполнение стека в разборе выражений ✅ — **исправлено (d0a5f79)**

`Parser` рекурсивный без ограничения глубины. Вставка в поле размера длинной
строки скобок, минусов или цепочки степеней → переполнение стека → вылет
(на Windows `FaultGuard` переполнение стека намеренно не ловит).

**Где:** `src/core/Expression.cpp` (`ParseExpr → ParseTerm → ParsePower → ParseUnary → ParsePrimary`).

**Стенд (ASan):** `stack-overflow` на 10 000 вложенных скобок, 200 000 унарных
минусов, цепочке `2^1^1^…`.

**Исправление:** счётчик глубины (например, 256) → `Error{"Слишком сложное выражение"}`;
плюс ограничение длины выражения (например, 4 КБ).

### B-11 — Испорченный `settings.json` — программа не запускается ✅ — **исправлено (a52a0bc)**

`Settings::Load` проверяет, что файл — JSON-объект, но дальше `j.value("uiScale", …)`,
`(*it)[0].get<int>()` бросают при несовпадении типа. Это до главного окна — то
есть программа падает **при каждом запуске**, пока пользователь сам не найдёт и
не удалит файл. Достаточно один раз руками поправить настройку («1,25» строкой
вместо числа) или откатиться на версию, где тип поля был другим.

**В программе:** `settings.json` = `{"uiScale":"1,25"}` → SIGABRT до появления
окна, `type must be number, but is string`. И так при каждом запуске.

**Где:** `src/app/Settings.cpp:22-82`. Тот же приём:
`src/app/Autosave.cpp:49,84-87` (`info.value("slot", …)`).

**Исправление:** весь `Load` в `try/catch(json::exception)` → значения по
умолчанию + `.bak` копия испорченного файла + уведомление. Писать файл
атомарно (B-18).

### B-12 — Огромная картинка текстуры: нехватка памяти и вылет 📖

`DecodeImage` раскрывает картинку целиком без ограничения размера. Фото с
телефона 8000×6000 → 192 МБ в памяти, плюс копии (вектор, текстура OpenGL, mip-уровни).
Специально сделанный PNG 30000×30000 весит килобайты, а раскрывается в 3,6 ГБ →
`std::bad_alloc` → вылет (B-06). Картинки лежат **внутри** `.bzc`, то есть
приходят вместе с чужими файлами.

Кроме того, у видеокарты есть предел размера текстуры (у встроенной графики
обычно 8192–16384 px), больше — текстура молча не создастся.

**Где:** `src/core/Image.cpp:11-22`; вызовы — `AppearanceEditor.cpp:493,564`,
`Viewport.cpp:463`.

**Исправление:** сначала `stbi_info_from_memory` — если больше, например,
4096×4096 или 64 Мп, — отказ; при импорте пользователем — уменьшать до 2048 по
большей стороне и хранить уже уменьшенную.

## Серьёзные (С)

### B-13 — Предупреждения эскизов исчезают после правки более поздней операции 📖

`RebuildSlice` начинается с `RecomputeModel(doc)`, который **для всех** эскизов
пересчитывает решатель и ставит статус «Ок». Но перестроение идёт только с
первой изменённой операции. Если эскиз стоит раньше, статусы, которые ставит
сама модель («Грань эскиза не найдена», «Часть проецированных рёбер не найдена»,
ошибка построения профиля), стираются и уже не восстанавливаются.

**Пример:** эскиз на грани, грань пропала — в дереве жёлтое предупреждение.
Пользователь меняет глубину выдавливания ниже по дереву → предупреждение
исчезает, хотя ничего не исправлено.

**Где:** `src/document/Recompute.cpp:8-41`, `src/kernel/Model.cpp:773`.

**Исправление:** решать эскизы только начиная с `FirstToRebuild` (это ещё и
ускорение, см. O-03); статус эскиза хранить раздельно «решатель» и «модель».

### B-14 — Все операции применяются только к последнему телу 📖 — нужно решение

Объединение, вычитание, пересечение, скругление, фаска, отверстие, оболочка,
зеркало тела — всё берёт `bodies.back()`. Резьба — исключение: она ищет тело
по грани.

**Пример:** тело 1, потом «Новое тело» 2, потом скругление ребра тела 1 →
«Рёбра операции не найдены». Вырез выдавливанием через оба тела режет только
второе.

**Где:** `src/kernel/Model.cpp` — `CombineSolid` (115), `ApplyEdgeFeature` (203),
`ApplyToLastBody` (232).

**Варианты:**
1. Автоматически: тело, которому принадлежат выбранные рёбра/грань (как сейчас
   у резьбы). Для вырезов — все тела, которые пересекает инструмент.
2. Как в Inventor: поле «Тела» в панели операции, по умолчанию — п. 1.

Рекомендация — 1 сейчас (без изменения формата файла), 2 — когда дойдёт до
многотельных деталей всерьёз.

### B-15 — Новые типы связей/кривых молча теряются при пересохранении 📖 — нужно решение

Загрузчик эскиза пропускает незнакомые типы связей и кривых («новее, чем
версия»). Файл открывается без предупреждения, а при сохранении эти данные
исчезают навсегда. Для операций сделано правильно (`UnknownFeature` хранит
JSON как есть), для содержимого эскиза — нет.

**Где:** `src/document/SketchFeature.cpp:217-224`.

**Варианты:** хранить незнакомые элементы сырым JSON и записывать обратно;
либо открывать такой файл только для чтения с предупреждением. Вы решили
учитывать совместимость с первой стабильной альфы — это пункт в список той
работы.

### B-16 — Два запущенных BreezeCAD мешают друг другу 📖 — нужно решение

- `running.lock` один на всех → второй экземпляр считает, что прошлый запуск
  упал.
- Окно восстановления показывает автосохранения **живого** первого
  экземпляра; «Восстановить» удаляет их папку.
- Второй экземпляр переименовывает лог первого в `.old` (на Linux/macOS).

**Где:** `src/app/Application.cpp:93-94`, `src/app/Autosave.cpp:73-91`, `src/core/Log.cpp:36-46`.

**Варианты:** (а) один экземпляр: второй передаёт файл первому и закрывается;
(б) несколько экземпляров: в `running.lock` писать PID и проверять, жив ли он;
у автосохранений — PID владельца. Inventor и КОМПАС — вариант (б).

## Средние (Ср)

### B-17 — Неудачный экспорт портит прежний файл 📖
`Export.cpp:76,109` пишет сразу в целевой файл. Ошибка посередине (диск,
сбой OCCT) → старый STL/3MF уже испорчен. **Исправление:** как в `WriteBzcArchive` —
во временный файл и переименовать.

### B-18 — Настройки сохраняются только при нормальном выходе 📖
`Settings::Save` вызывается в конце `Run()`. После вылета пропадают недавние
файлы, клавиши, размер окна (на стенде: после снятия процесса `settings.json`
так и не появился, хотя за сессию открывались файлы). Запись неатомарна (`ofstream` поверх). **Исправление:**
сохранять при изменении (с задержкой ~1 с), атомарно через временный файл.

### B-19 — Модуль с неудачным `init` выгружается без `shutdown` 📖 — нужно решение
`ModuleManager::Load`: при `rc != BZ_OK` библиотека закрывается, а модуль мог
успеть запустить поток или подписаться на что-то → вылет после выгрузки.
Решение для ABI: «`shutdown` вызывается всегда, если `init` был вызван» —
записать в `bz_module.h` и сделать. Также исключение C++ из модуля через C-ABI
— неопределённое поведение; `Call` стоит обернуть хотя бы `catch (...)`.

### B-20 — Сбой обхода папки автосохранений на старте 📖 — **исправлено (63754c0)**
`Autosave::FindRecoverable`: `entry.is_directory()` без `error_code` бросает при
отказе в доступе (антивирус, OneDrive) → вылет до появления окна.
Аналогично `BetaTesting.cpp:82,176,200`. **Исправление:** `is_directory(ec)`.

### B-21 — Массив в эскизе до 500×500 копий 📖
Поле количества ограничено 500 **в каждом направлении** — 250 000 копий.
Решатель плотный (см. O-01): уже ~1000 копий элемента со связями — секунды,
десятки тысяч — гигабайты памяти и `bad_alloc`. **Исправление:** ограничить
произведение (например, 2000 копий), предупреждать при > 300.

### B-22 — Утечка при каждом перехваченном падении OCCT 📖
Всё, что было на стеке (векторы, ручки OCCT), не освобождается — так и написано
в `FaultGuard.h`. Уйдёт вместе с решением B-07.
