# Аудит BreezeCAD — качество кода и оценки

Оценивал как опытный C++-программист, который открывает проект впервые и
должен в нём работать. Проект: ~42 700 строк своего кода C++20 (`src/`),
~5 600 строк тестов (205 тестовых случаев), без учёта `third_party/`.

## Оценки

Шкала — «сколько нервных клеток из 10 сохранит» (10 — ни разу не выругается).

| Кто | Сейчас | После исправлений из этого аудита |
|---|---:|---:|
| **Программист**, который придёт в проект | **6,5 / 10** | **8,5 / 10** |
| **Пользователь** на слабом ноутбуке | **5 / 10** | **8,5 / 10** |

**Почему программист — 6,5, а не меньше.** Для проекта такого размера,
собранного с помощью нейросетей, код необычно аккуратный: слои с правилом
«стрелки только вниз», объяснения «почему» в комментариях, единый стиль имён,
обработка ошибок через `Expected/Status`, а не исключениями, отмена через
команды, ссылки на геометрию по описанию, а не по индексам OCCT, тесты ядра.
Человек найдёт, куда идти, за 10–15 минут — `docs/ARCHITECTURE.md` написан
хорошо.

**Почему не 8+.** Несколько вещей, на которых он выругается (перечислены ниже):
файлы по 1 000–1 800 строк при собственном правиле «не больше 500», лестница из
17 `dynamic_cast` в сердце перестроения, редакторы-одиночки на всё
приложение (отсюда B-05), неровная защита загрузки файлов (часть полей
проверяется, часть — нет), и `FaultGuard` — хитрый низкоуровневый код, который
нужно понимать вместе с потрохами OCCT.

**Почему пользователь — 5.** Вылетов на «обычной» работе немного — бета-тесты
это подтверждают. Но есть дешёвые способы потерять работу: открыть файл, когда
другой открытый файл переместили (B-04); открыть чужой повреждённый файл (B-01);
опечатка в угле (B-03); переключить вкладку посреди операции (B-05). Плюс на
слабом железе — графика «Высокое» по умолчанию и плотный решатель (O-01, O-02).
После исправлений из `01-bugs.md` (все 12 критичных — это в сумме несколько
дней работы) и O-01…O-04 остаются только «обычные» для CAD шероховатости.

## Что хорошо (не трогать)

1. **Слои и зависимости.** `core → sketch → document → kernel → render/ui → app`,
   и правило соблюдается: `sketch` и `document` не знают про OCCT и ImGui,
   поэтому тестируются без окна. Это редкость даже в профессиональных проектах.
2. **Ошибки — значениями.** `Expected<T>` / `Status` с русским текстом для
   пользователя. Исключения — только на границе с OCCT/JSON.
3. **Отмена через команды** (`doc::Command`), правка «на месте» с копией «до» —
   единообразно для эскиза и операций.
4. **Ссылки на геометрию по описанию** (`FaceReference`, `EdgeReference`), а не
   по номерам граней — то, на чём ломаются многие любительские CAD.
5. **Комментарии объясняют «почему»**, а не «что». Нет ни одного `TODO/FIXME`.
6. **Нет голых `new`/`delete`** (кроме ручек OCCT, где так принято).
7. **Перестроение кусками и в фоне** на копиях — продуманно, без гонок.
8. **Тесты ядра**: эскиз, документ, операции OCCT, сборки, модули. И
   `SourceRulesTests` — тесты, которые проверяют правила самого кода. Хорошая идея.
9. **Монитор и бета-сборка** (`core/Monitor`, `tools/monitor`) — сбор вылетов и
   зависаний с последним действием. Редко кто так делает на этой стадии.

## Что заставит программиста выругаться

**Заметные:**

- **Q-01 — Большие файлы** при собственном правиле «не больше 500 строк»
  (`RULES.md` п. 21): `SketchTools.cpp` 1770, `Viewport.cpp` 1431, `Model.cpp` 1228,
  `AssemblyUi.cpp` 1150, `Dialogs.cpp` 1116, `StandardParts.cpp` 1093 — всего 13
  файлов больше 500. Предложение: `SketchTools.cpp` → по группам инструментов
  (рисование / правка / связи / массивы); `Dialogs.cpp` → по окну на файл;
  `StandardParts.cpp` — таблицы данных вынести в JSON в `assets/`.
- **Q-02 — Лестница `dynamic_cast` в `Model::RebuildSlice`** (`Model.cpp:812-937`):
  каждая операция — ветка `else if (auto* x = dynamic_cast<…>)`. Новая операция =
  правка в середине самой опасной функции программы. Лучше: у каждой операции
  ядра свой «применитель», регистрируемый так же, как `FeatureRegistry`
  (`kernel::ApplierRegistry`), — тогда `RebuildSlice` станет короткой и
  обработка ошибок будет в одном месте.
- **Q-03 — Редакторы операций и эскиза — одни на всё приложение**
  (`OperationEditors`, `SketchEditor` в `Application`), а данные — в документе.
  Отсюда B-05. Редактор должен принадлежать сессии или хотя бы помнить её.
- **Q-04 — Неровная защита ввода.** В одних местах загрузчики аккуратно
  проверяют типы (`ReadMember`, `JsonIO.cpp`), в других — `value()` и `get<>()`
  без проверки (B-01, B-11). Нужен один набор безопасных функций чтения и
  правило «в загрузчиках только они» — его можно проверять в `SourceRulesTests`.

**Помельче:**

- **Q-05** — «Добавить инструмент эскиза» = 7 мест в 6 файлах (это честно
  описано в `ARCHITECTURE.md`, но это всё равно 7 мест). Таблица инструментов с
  размером массива, который надо руками увеличить на 1, — ловушка.
- **Q-06** — Ключи перевода = русский текст. Удобно автору, но иностранный
  участник не поймёт, что менять, а правка опечатки в русском тексте ломает все
  переводы. Не срочно; если появятся переводчики — перейти на ключи-идентификаторы.
- **Q-07** — Нижние слои (`document`, `kernel`) возвращают пользовательский
  русский текст ошибок. Для одного языка удобно, для модулей и MCP — неудобно:
  стоит добавить к `Error` машинный код (`ErrorCode::FaceNotFound`).
- **Q-08** — `ModuleHost.cpp` — глобальные переменные (`gReader`, `gComponents`).
  Пока модулей мало — ладно; при появлении потоков — гонки.
- **Q-09** — `RULES.md` обещает `clang-format`, но файла `.clang-format` в
  репозитории нет. Стиль сейчас ровный за счёт дисциплины, а не инструмента.
- **Q-10** — `docs/legacy` — 1,8 МБ старых заметок и промптов в основном
  репозитории. Программист потратит время, пытаясь понять, актуально ли это.
  Перенести в вики или в отдельную ветку `archive`.
- **Q-11** — `docs/RULES.md` смешивает правила **кода** с правилами **работы с
  нейросетью** («только консольные команды», «быть тёплым»). Живому
  программисту стоит выдать отдельный `CONTRIBUTING.md` (он есть, но
  `RULES.md` называет себя «единственным источником правды»).
- **Q-12** — Нет тестов слоя `app` (интерфейс): все проверки — через скрипты
  Xvfb и монитор. Для сценариев вроде B-05 (вкладки + редактор) нужен хотя бы
  «безголовый» тест `Workspace + OperationEditors` без отрисовки.

## Сборка и тесты

- Предупреждения компилятора строгие (`-Wall -Wextra -Wconversion -Wshadow …`) —
  отлично. Но `-Werror` в CI нет — предупреждения могут копиться незаметно.
- Санитайзеры (ASan/UBSan) в CI не запускаются. Одна linux-задача с
  `-fsanitize=address,undefined` поймала бы B-02 и B-10 автоматически.
  Предложение: отдельный пресет `linux-asan` и ночной (или по кнопке) прогон
  `bz_tests` и фаззеров загрузки.
- Фаззер загрузки файлов и выражений из этого аудита лежит в
  `tests/audit/` (см. README) — его стоит превратить в обычные тесты doctest после
  исправлений.
