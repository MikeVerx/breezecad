# BreezeCAD — Формат файлов `.bzc`

**Единый источник правды о хранении документов.**
**Дата:** 2026-09-23
**Статус:** утверждён

---

## 1. Философия

**Главное правило:** файлы старых версий открываются в новых. Всегда.
Даже через 5 лет.

Следствия:
1. **Не используем OCAF** для основного формата — привязка к версии OCCT.
2. **Своя структура** с явным версионированием.
3. **Миграции обязательны.** Каждая новая версия умеет читать все старые.
4. **Явные версии в файле.** При загрузке знаем, с чем работаем.

Референсы: Eyeshot (явный FileHeader), Mudbox (сериализация операций).
FreeCAD — как НЕ надо (нет версионирования).

---

## 2. Структура `.bzc`

Файл `.bzc` — ZIP-контейнер со строго определённым содержимым.

    model.bzc (ZIP, deflate)
    ├── manifest.json          обязательно, точка входа
    ├── history.bin            параметрическая история
    ├── geometry.brep          кэш B-rep (пересчитывается)
    ├── tessellation.bin       кэш триангуляции
    ├── parameters.json        переменные и формулы
    ├── materials.json         материалы
    ├── preview.png            превью 512x512
    └── thumbnails/            виды, эскизы

### 2.1. manifest.json

Читается первым. Определяет, как читать остальное.

Поля:
- format_version — версия .bzc (не программы!)
- app_version — версия BreezeCAD
- occt_version — для диагностики кэша
- created / modified — временные метки
- units — мм / см / м / дюйм
- document_type — part / assembly / drawing
- document_name — отображаемое имя
- features_count — число операций
- compression — метод сжатия

### 2.2. history.bin

Основной источник правды. Все операции в порядке применения.
Бинарный, собственная сериализация.

Структуры:
- DocumentHeader: magic 'BZCH', version, op_count, timestamp
- OperationRecord: type, op_version, id, parents[], name, params, blob_data

Ключевые решения:
- ID операций — uint64_t, монотонный счётчик. Не переиспользуются.
- parents — граф зависимостей.
- blob_data — тяжёлые данные (точки кривых, эскизы).
- Версия у КАЖДОЙ операции — можно менять Extrude независимо от Fillet.

### 2.3. geometry.brep

Кэш B-rep через BRepTools::Write().
- occt_version совпадает — используем кэш.
- отличается — игнорируем, пересчитываем из history.
- При сохранении всегда обновляем.

### 2.4. tessellation.bin

Собственный бинарный. Header 'BZCT', version, shape_count.
Для каждого shape: shape_id, vertex_count, triangle_count, vertices, normals, indices.
Если устарел — пересчёт в фоне. UI не блокируется.

### 2.5. parameters.json

Список переменных: name, value, unit, formula, comment.

### 2.6. materials.json

assigned: feature_id -> material.
library: определение материала (название, плотность, цвет).

### 2.7. preview.png

Скриншот 512x512 для Home Screen.

### 2.8. thumbnails/

top.png, front.png, right.png, iso.png. sketch_<id>.png для эскизов.

## 3. Версионирование

### 3.1. Схема

MAJOR.MINOR.PATCH:
- MAJOR — ломающие (старые читаются с миграцией).
- MINOR — добавления (совместимо).
- PATCH — исправления.

### 3.2. Правила

- Файл MAJOR.MINOR новее — предупреждаем, открываем read-only.
- Файл старее — запускаем миграцию.
- Тот же MAJOR — читаем напрямую.

### 3.3. Миграции

Каждая миграция — отдельная функция migrate_vX_to_vY(data).
Цепочка upgradeToCurrent(data, fileVer).

Правила:
- Никогда не удаляем старые миграции. Даже через 5 лет.
- Миграции идемпотентны.
- Логируем: «Migration 1.0 -> 1.1: 5 операций обновлено».
- Падение миграции — не открываем файл, показываем диалог.

## 4. Несовместимость

### Сценарий 1: битый ZIP

Пробуем восстановить из целых частей. Если history.bin целый —
пересчитываем геометрию. Показываем прогресс.

### Сценарий 2: неизвестная операция

Файл новее — пропускаем незнакомые операции, предупреждаем.
Показываем список: «sheet_metal_bend (v2.0), weld_seam (v2.0)...».

### Сценарий 3: OCCT-кэш несовместим

Просто пересчитываем из истории. Прогресс-бар.

## 5. Кэширование

**Правило:** с момента введения .bzc кэшируем тяжёлое.

Что кэшируем:
- B-rep каждой операции (в памяти + geometry.brep).
- Триангуляция (tessellation.bin).
- Bounding box (в history.bin).
- МЦХ: масса, объём (в history.bin).
- Превью (thumbnails/).

Инвалидация: операция изменилась -> все потомки инвалидируются.

LRU-кэш в памяти: последние N результатов (N=50, по бюджету RAM).

Ленивое вычисление: невидимое на экране — не считаем, пока не понадобится.

## 6. OCAF как модуль

OCAF — мост совместимости для .cbf. Читает старые, конвертирует в
наш DocumentData, сохраняет как .bzc. Мы .cbf никогда не пишем.

Порядок:
1. Пользователь открывает .cbf.
2. Проверяем: установлен ли модуль OCAF?
3. Нет — предлагаем установить. Да — читаем через OCAF.
4. Конвертируем в DocumentData.
5. Сохраняем как .bzc.

## 7. Экспорт

- STEP — STEPControl_Writer, AP214, все B-rep тела.
- STL — StlAPI_Writer, настройки точности.
- Импорт STL — только через STL Viewer (измерения). Полный импорт
  геометрии — Фаза 3+.

---

## 8. Полный цикл

### Сохранение

1. Ctrl+S.
2. Собираем DocumentData (history, parameters, materials).
3. Пишем во временный .bzc.tmp.
4. Zip: manifest + history + geometry + tessellation + ...
5. Atomic rename: .bzc.tmp -> .bzc.
6. Обновляем preview.png.

### Загрузка

1. Открыть .bzc.
2. Прочитать manifest.json.
3. Проверить format_version.
4. При необходимости — миграции.
5. Прочитать history.bin.
6. geometry.brep валиден по occt_version — использовать.
   Иначе — пересчёт в фоне + прогресс-бар.
7. Показать модель.

## 9. Зарезервированные слоты

- plugins/ — данные плагинов.
- variants/ — конфигурации (Фаза 7+).
- drawings/ — чертежи (модуль).
- simulation/ — FEA (если будет).

Правило: неизвестные файлы игнорируются при загрузке.

---

## 10. Правила для нового чата

1. Формат .bzc обязателен. Не менять схему без ADR.
2. Миграции не удаляем. Даже через 5 лет.
3. Кэширование — часть формата.
4. OCAF — только мост для .cbf.
5. Любое изменение структуры — новая версия + миграция + ADR.
