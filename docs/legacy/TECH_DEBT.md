## TECH-DEBT-001: Белый экран при запуске без gdb [FIXED]

**Статус:** FIXED (2026-09-21)
**Приоритет:** HIGH (был)
**Дата заведения:** 2026-09-21
**Дата исправления:** 2026-09-21

### Финальный диагноз

`OSD_MemInfo::Value(OSD_MemInfo::MemWorkingSet)` под MinGW внутри
**вызывает `wmic` через `popen()`**. В Windows 11 24H2+ `wmic.exe`
удалён из системы. `popen()` получает код возврата 127, и программа
завершается без диагностики — окно остаётся белым.

Почему выглядело «плавающим»: первые 1-2 запуска после пересборки
работали — Windows Defender ещё не пометил свежий exe как «новый».
Потом все последующие запуски стабильно падали на `UpdateTelemetry`.

### Исправление

Заменено на прямой WinAPI-вызов `GetProcessMemoryInfo()` из `psapi`
(системный вызов k32, никаких внешних процессов).

### Что помогло найти баг

TRACE-инструментация главного цикла с env-переменной `BREEZECAD_TRACE`:
она показала, что trace обрывается ровно между `before UpdateTelemetry`
и `after UpdateTelemetry`. Серия из 5 запусков подтвердила детерминизм.

### Исторические попытки (все не помогли)


### Симптом

Приложение при запуске показывает белое окно. Логи доходят до
`InitCommands: 15 commands loaded` и на этом останавливаются.
GUI не рисуется.

При запуске через `gdb --batch -ex run -ex args ./breezecad.exe` —
программа стартует нормально (не всегда, но часто).

### Что уже проверено и НЕ помогло

1. **Полная пересборка** (`rm -rf build && cmake -B build -G Ninja && ninja`).
   Иногда помогает, иногда нет. Нестабильно.
2. **`ninja -t clean && ninja`.** Аналогично — иногда помогает.
3. **Отключение ImGui рендера** (`ImGui::Render` + `ImGui_ImplOpenGL3_RenderDrawData`
   закомментированы). Не помогло — белый экран остался.
4. **`taskkill //F` перед запуском** (гипотеза: висящий GL-контекст).
   Убрано из `run.sh` — гипотеза не подтвердилась.
5. **Явное `glfwMakeContextCurrent` перед ImGui NewFrame и RenderDrawData.**
   Добавлено в код — не помогло.
6. **`glViewport(0, 0, fbW, fbH)` перед RenderDrawData.** Не помогло.
7. **Манифест** — стандартный Windows-манифест с `supportedOS` для Win7-Win11,
   `asInvoker`. Ничего подозрительного.
8. **GLFW 3.5.1** — актуальная версия.
9. **Compatibility Profile** (`contextCompatible = true`) — уже включено
   в `OcctView::Init`.
10. **Debug-trace** по точкам: конструктор `Application`, вход в `Run()`,
    главный цикл, `PollEvents`, `NewFrame`, `OcctView::Redraw`,
    `RenderDrawData`, `SwapBuffers` — все проходят. Проблема дальше, в
    самой отрисовке GL.

### Что установлено точно

- Логи `std::cout` идентичны в рабочем и нерабочем режиме.
- Debug-точки идут **до** `SwapBuffers` и `After SwapBuffers` в обоих режимах.
- Приложение не падает — процесс жив, крутит цикл.
- Проблема не в коде логики: она в **GL-состоянии** или **порядке инициализации**.
- `taskkill /F` не связан (проверено).

### Возможные направления для поиска

1. **Проверить, какой GL-контекст активен** в момент `RenderDrawData`.
   Вывести `glfwGetCurrentContext()` и сверить с `myWindow->GetNativeWindow()`.
2. **Проверить `Aspect_NeutralWindow` + `SetWindow`** в `OcctView::Init` —
   OCCT создаёт свой контекст поверх GLFW. Возможно, между ними race.
3. **`glfwSwapInterval(1)`** — VSync. Попробовать без него (0) — иногда
   на слабых драйверах VSync блокирует первый кадр.
4. **Попробовать `glFinish()`** после `SwapBuffers` — вдруг асинхронный
   swap не успевает.
5. **Тайминги инициализации.** Возможно, `OcctView::Init` вызывается
   слишком рано после `glfwCreateWindow` — драйвер не готов. Попробовать
   `glfwWaitEvents()` + небольшая задержка.
6. **Двойная инициализация GLFW.** Проверить, что `glfwInit()` вызывается
   ровно один раз (в `GlfwWindow` конструкторе).
7. **Проверить размер framebuffer.** Возможно, `fbW=0, fbH=0` в момент
   первого `FitAll` / `Redraw`, и рендер уходит в никуда.
8. **Проверить `myOcctView->Init` на возврат `false`** — сейчас код делает
   `myOcctView.reset()` и `return`, что оставляет Application в
   нерабочем состоянии без сообщения пользователю.

### Наблюдение 2026-09-21 (позднее)

Баг **плавающий**. При добавлении TRACE-точек в главный цикл
наблюдалось:

- В **рабочем** запуске: все TRACE-точки проходят до `SwapBuffers`,
  включая `UpdateTelemetry`, `DrawHomeScreen`, `DrawSettingsDialog`.
- В **падающем** запуске: trace обрывается между `ui: DrawRightPanel end`
  и `ui: before DrawHomeScreen`. При этом `[DIAG] Frame 0` не выводится.
- **GL-ошибок нет** (`err=0x0`), контекст совпадает
  (`glfwGetCurrentContext == glfwGetNativeWindow`), framebuffer корректный
  (1280x720).

То есть программа не падает, не крашится, GL-ошибок нет — но кадр
не выводится. Это указывает на **гонку в драйвере или ОС**, а не на
логику приложения.

Триггер: **после пересборки** (`ninja`). Первый запуск после сборки
почти всегда даёт белый экран. Второй+ запуски работают. gdb замедляет
старт и «лечит» проблему.

Вероятная причина: **Windows Defender** сканирует свежесобранный exe
при первом запуске, что вызывает задержку инициализации GL-контекста.
Либо драйвер видеокарты кэширует шейдеры и не успевает на первом старте.

### Обходной путь (текущее решение)

`run.sh` использует **gdb --batch** для запуска. Работает нестабильно,
но чаще всего запускает приложение.
**Это костыль, требует исправления.**

## TECH-DEBT-002: Кириллица в пути SaveAs → кракозябры

**Статус:** OPEN
**Приоритет:** MEDIUM

### Симптом

Сохраняя документ в `C:\Users\Мишаня\Downloads\123.cbf`, OCAF выводит:
Файл сохраняется, но с битым путём в логе.

### Гипотеза

Проблема в `Utf8ToExt` / `TCollection_ExtendedString` при конвертации
кириллицы. Используется `(wchar_t*)` как если бы `wchar_t` был 16-bit,
но на MinGW это может быть 32-bit (зависит от настроек).

### Что попробовать

- Проверить `sizeof(wchar_t)` в MinGW.
- Использовать `TCollection_ExtendedString(const char*, Standard_Boolean isMultiByte)`
  напрямую вместо ручной конвертации.
- Или передавать `std::filesystem::path::wstring()` — тоже аккуратно.

## TECH-DEBT-008: FPS 30 на мощном ноуте (Legion 5 Pro)

**Статус:** OPEN
**Приоритет:** MEDIUM

### Симптом

На Lenovo Legion 5 Pro (R7 5800H, RTX 3060 Laptop, 32 ГБ DDR4) при работе
от батареи FPS = 30. Приложение лёгкое (160-165 FPS на рабочем ПК).

### Возможные причины

1. **Питание от батареи** — Windows power plan «Экономия», CPU в 800 МГц,
   GPU в мин. режиме.
2. **Nvidia Optimus** — приложение пошло через iGPU Radeon вместо RTX 3060.
3. **VSync + 30 Гц монитор / DWM-композиция** — ограничение.
4. **Термотроттлинг** — ноут перегрет.

### План диагностики

1. Запустить с `BREEZECAD_TRACE=1` — посмотреть время в `SwapBuffers`:
   - 33 мс → VSync/30 Гц.
   - 30 мс в `Redraw` → CPU/GPU тормозит.
2. Ввести env `BREEZECAD_NO_VSYNC` — отключить `glfwSwapInterval(0)`.
3. В Nvidia Control Panel — принудительно RTX 3060 для `breezecad.exe`.
4. `powercfg /getactivescheme` — проверить план.

### Гипотеза

80% — питание от батареи + power plan.

## TECH-DEBT-009: Вёрстка ribbon — 10+ итераций

**Статус:** RESOLVED (коммит 5003fab)
**Приоритет:** был HIGH

### Что помогло

1. **Стрелка ▼ — вертикальная полоса справа от кнопки** вместо отдельной
   полосы под кнопкой. Решило проблему разной высоты групп раз и навсегда.

3. **Фиксированный TARGET_H = 74** для всех групп.
4. **Горизонтальный скролл child** вместо скрытия кнопок в выпадашку.
5. **Никаких `..`** в UI — рендерится как `?`. Вместо этого уменьшение

### Урок

Борьба шла из-за **правильной архитектуры**: когда стрелка «съедала»
отдельные 12-14 px под каждой кнопкой, ни одна высота не совпадала.
Как только убрали эту полосу вправо — всё выровнялось.

## Заметки о workflow

### Что работает хорошо

- **Python heredoc** (`python << 'PYEOF'`) для правок — сохраняет CRLF,
  не ломает UTF-8.
- **`grep -a`** для UTF-8 файлов.
- **`objdump -p | tr -d '\0' | grep -aE 'DLL Name:' | awk '{print $3}'`**
  для получения зависимостей DLL.
- **`LC_ALL=C`** для предотвращения локализованного вывода objdump.

### Уроки (lessons learned)

**Regex-патчи по C++ — опасны.** Попытка убрать блок `[DIAG]` через
`re.compile(...re.DOTALL)` съела закрывающую скобку `try {}`, из-за чего
файл перестал компилироваться (`expected catch before }`).

**Правила на будущее:**

1. Перед каждым патчем — `git commit` или бэкап `.bak`.
2. После каждого патча — **сразу сборка** (`ninja`).
3. Если сборка упала — **немедленно** `git checkout -- <файл>`, не
   пытаться «докрутить» фикс поверх сломанного файла.
4. Regex применять только для **однострочных** замен. Для блоков кода —
   либо точное совпадение строк (`.replace()` без regex), либо несколько
   отдельных патчей с проверкой между ними.
5. Если патч затрагивает структуру (скобки, `{}`, `try/catch`) — нужен
   ручной просмотр результата до компиляции.

### Что не работает / опасно

- **`sed -i`** — ломает CRLF (весь файл переписывается LF-переводами).
- **`grep` без `-a`** — файл считается бинарным, поиск молчит.
- **Кириллица в `python -c "..."`** — синтаксические ошибки.
- **`taskkill //F`** — не связано с текущим багом, но вообще грубо.

### Правила для следующего чата

1. Правки только через консольные команды. Не «открой файл в редакторе».
2. После каждой правки — команда проверки (grep/diff).
3. После сборки — команда запуска для теста.
4. Не предлагать ребут как решение.
5. Если что-то сломалось после изменения — откатывать целиком, не «докручивать».
