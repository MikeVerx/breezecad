# Памятка для ассистента: исправление багов в ветке `fix/beta`

Вставь этот файл целиком в начало чата. Работаем только в ветке `fix/beta`.
В `next` и `main` ничего не сливать и не пушить — это делает владелец после проверки.

## Проект
BreezeCAD — САПР на C++20: ImGui (интерфейс), OpenCASCADE (геометрия), doctest (тесты).
Код в `src/` (core, sketch, document, assembly, kernel, render, app, ui, platform), тесты в `tests/`.

## Сборка и тесты (Linux)
```bash
git switch fix/beta && git pull
cmake --preset linux-debug
cmake --build --preset linux-debug -- -k 0 2>&1 | grep -E "error|warning:" | head
./build/linux-debug/bin/bz_tests 2>&1 | tail -1     # должно быть: Status: SUCCESS!
./build/linux-debug/bin/breezecad                   # запустить программу
```
Пакеты (Ubuntu): `libocct-*-dev libtbb-dev libglfw3-dev libgl1-mesa-dev`.

## Порядок работы над одним багом
1. Взять баг из `docs/dev/BETA-BUGS.md`. Если не понятно, как воспроизвести, — спросить.
2. Найти место через поиск (`grep -rn "текст с экрана" src/`), а не читать большие файлы целиком.
3. Исправить **минимально и точечно**. Не переписывать файлы, не «наводить порядок» рядом.
4. Собрать, прогнать `bz_tests`. Если баг в логике (не в отрисовке), добавить тест в `tests/`.
5. Один баг — один коммит (формат ниже). Записать в `BETA-BUGS.md` статус и хеш коммита.

## Правила кода (обязательно)
- Английские идентификаторы и комментарии, UTF-8, переводы строк LF.
- Видимый текст интерфейса — только через `Tr("…")` или `Trf("… {}", x)`. В статических
  таблицах — `N_("…")`, а при показе `Tr(...)`. Нельзя `ImGui::Text(Tr("…"))` —
  только `ImGui::Text("%s", Tr("…"))`.
- Нижние модули (document, kernel, core, assembly) пишут сообщения по-русски целыми
  шаблонами `std::format("… {}", x)`; интерфейс переводит их `Tr(std::string)`.
- После новых строк интерфейса: `python3 scripts/i18n/extract.py`, и закоммитить
  `translations/template.json` вместе с исправлением.
- Цвета — только токены темы (`ui.C().text`, `ui.C().danger` …), никаких `0xFF…`.
- Не называть переменные `far` и `near` (макросы windows.h — ломают сборку под Windows).
- Без телеметрии и сетевых запросов: программа офлайн.

## Не трогать без владельца
Формат файлов (`document/BzcFile*`, `document/JsonIO*`, `assembly/AssemblyFile*`),
решатель сборки (`assembly/Solver*`), `kernel/AssemblyModel*`, `kernel/AutoDrop*`,
`kernel/ComponentPattern*`, `CMakeLists.txt`, `.github/`. Если баг там — описать его
в `BETA-BUGS.md` (что, где, догадка о причине) и оставить статус «не исправлено».

## Формат коммита
```
<область>: <что исправлено, коротко по-английски>

What: что изменилось для пользователя.

Why: баг №N из BETA-BUGS.md — что было не так и почему.

Where: файлы/функции.

Tested: bz_tests N/N; как проверено руками (Linux / Windows-билд).
```
Область — `app`, `sketch`, `kernel`, `ui`, `document` и т. п. Пример: `git show c0bfa3d`.

## Чего не делать
- Не исправлять несколько багов одним коммитом.
- Не менять поведение «заодно», не обновлять зависимости, не трогать `third_party/`.
- Не удалять и не ослаблять существующие тесты, чтобы они проходили.
- Не делать `git push --force`, `rebase` опубликованных коммитов, слияния в `next`.
- Если не уверен в причине — лучше описать находку в `BETA-BUGS.md`, чем гадать в коде.
