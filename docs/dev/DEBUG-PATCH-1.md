Один чат = один этап. В конце этапа: обновить «Статус» в таблице ниже, закоммитить, пушнуть один раз.

## Как работать (читать каждому чату)

1. Старт: `git switch fix/beta-1 && git pull -q`, сборка и тесты — HANDOFF.md §0. Правила кода
   и коммитов — HANDOFF.md §1, экономия токенов — §2. Больше из HANDOFF ничего не читать.
2. Взять **первый** этап со статусом «не начат» или «в работе». Другие этапы не трогать.
3. Порядок по каждому багу: найти место (`grep -n`, потом `sed -n a,bp`) → понять причину →
   минимальная правка → сборка → `bz_tests` → тест на логику, если баг не в отрисовке → коммит.
   Один баг — один коммит (What/Why/Where/Tested). В Why — номер бага отсюда (Б1, Б2…).
4. Если причина не находится за разумное время — записать находки в «Заметки» этапа,
   статус «нужны данные», и остановиться. Не гадать в коде.
5. Вопросы к Мише — только если без ответа нельзя продолжать; задать всё одним сообщением.
6. Отчёт в чат в конце — не больше 10 строк: что исправлено (хеши), что проверить Мише
   на Windows-сборке, что осталось.

Windows-сборку собирает только CI (`next-build`). Всё, что проверяется только на Windows
(Б1 обязательно), Миша проверяет сам на сборке после слияния — отметить «проверить на Windows».

## Этап 1. Б1 — вылеты (сопряжение, резьба, выдавливание до грани)

**Что уже известно (разобрано 2026-10-12 по трём отчётам тестеров, сборка 0.2.0 от 2026-10-11):**
- Три вылета, три разных ПК (RTX 4060 Ti / RTX 3060 / Vega 8), три команды
  (`feature.fillet`, `feature.thread`, `feature.extrude` до грани). Железо ни при чём.
- Стек у всех трёх один и тот же (breezecad.exe несёт символы — `nm -C breezecad.exe`):
  `main → Application::Run → Application::Frame → Session::Rebuild → Model::RebuildSlice
  → guard::RunGuarded(+0x259) → std::format (__do_vformat_to) → libstdc++ → 0xC0000005`,
  чтение по адресу `0x18`.
- Значит: при перестроении OCCT упал внутри операции, `RunGuarded` (src/core/FaultGuard.cpp,
  Windows-ветка, `__builtin_setjmp/longjmp`) этот сбой **поймал**, а потом программа упала
  уже в его собственном пути возврата — в `if (what) *what = Describe();`
  (`std::format("исключение 0x{:08x}", tlCode)`). Защита 5466ae0 на Windows не спасает,
  а превращает сбой операции в вылет.
- Перед вылетом в логе: сопряжение — «радиус слишком большой?»; резьба — ждала грань,
  тестер закрывал панель; выдавливание — ждало целевую грань (тело вращения).

**Задачи по порядку:**
1. Путь возврата `RunGuarded` на Windows. После прыжка — никакой работы с кучей/locale/format:
   код сбоя уже лежит в `tlCode`; строку собрать после выхода из `RunGuarded` (или простой
   `snprintf` в буфер на стеке). Проверить, что `what` и прочие переменные, нужные после
   `setjmp`, не теряются (volatile / чтение из памяти). Рассмотреть и более надёжный путь:
   из обработчика не прыгать, а бросать C++-исключение (как OCCT на MSVC через
   se_translator) — тогда стек раскручивается, деструкторы и цепочка
   `Standard_ErrorHandler` OCCT не остаются висеть. Выбрать вариант, обосновать в коммите.
   Если сбой OCCT — следствие порчи кучи, прыжок не поможет ни в каком виде: тогда записать
   это и переходить к п. 2.
2. Найти исходные сбои OCCT (Linux, `linux-debug`, gdb; HANDOFF §6а — прошлый разбор:
   `Extrema_ExtCC::Perform` под `BRepClass3d_SolidClassifier`):
   - сопряжение слишком большим радиусом на цилиндре, стоящем в другом цилиндре;
   - выдавливание «до грани» с целью на теле вращения / криволинейной грани;
   - резьба: почему закрытие панели без выбранной грани вообще запускает перестроение
     (`src/app/features/ThreadEditor.cpp`, `src/document/ThreadFeature.cpp`).
   Где можно — проверить входные данные до вызова OCCT и вернуть понятную ошибку операции.
3. Тест в `tests/` на путь возврата `RunGuarded` (Linux-ветка тестируется; Windows-тесты
   FaultGuard пропущены — см. 06ecad2, не включать без понимания).
- **Готово, когда:** на Linux сценарии п. 2 не валят программу; на Windows — Миша
  повторяет три сценария на новой сборке (отметить «проверить на Windows»).
- **Не делать:** глушить все исключения подряд, возвращать «успех» при сбое.

**Заметки:**
- 2026-10-12, п.1 — `ddb429a`. Причина подтверждена дизассемблером `RunGuarded` из exe беты 0.2.0
  (GCC 16.2 MSYS2; `objdump -d --start-address=0x140485670`): в пути после `__builtin_setjmp`
  встроенный `std::format` собран с нулями вместо vptr и буфера приёмника и указателя на аргументы
  (`pxor %xmm0` + `movups` в слоты 0x110/0x118/0xe8/0xf0) → первый виртуальный вызов читает 0x18,
  адрес возврата `+0x259`. Путь «без `what`» собран верно. Решение: приёмник прыжка — отдельная
  `RunLanded` (noinline+noipa), после прыжка только `return false`; `Describe()` — снаружи.
  Вариант «бросить C++-исключение из обработчика» отвергнут: OCCT из MSYS2 собран без
  `-fnon-call-exceptions`, для сбойной инструкции нет call-site → personality зовёт `std::terminate`.
- Остаточный риск: объекты OCCT на брошенном стеке не разрушаются (утечка, как и раньше на Linux);
  если сбой был внутри `OCC_CATCH_SIGNALS`, его `Standard_ErrorHandler` может остаться в цепочке.
  Если после пойманного сбоя будут вылеты в следующей операции OCCT — смотреть сюда.
- Тесты FaultGuard на Windows по-прежнему пропущены (06ecad2); новый тест пути возврата
  (`FaultGuardTests.cpp`) прогнан только на Linux, FaultGuard собран отдельно (g++ 13, -O0/-O2).
  Полный `bz_tests` не собирался: в этом контейнере apt закрыт прокси (archive.ubuntu.com,
  conda, msys2 — недоступны), OCCT не поставить. **Следующему чату:** проверить сборку и
  `bz_tests` по HANDOFF §0, затем п.2.
- п.2, резьба (статически): панель при открытии сразу вставляет элемент-превью
  (`FeatureOperationEditor::OpenNew` → `doc.Insert`), при отмене убирает (`Cancel` → `doc.Take`) —
  оба раза перестроение, так задумано. Без грани `occt::Plan` (Thread.cpp) возвращает ошибку
  до любого вызова OCCT, `ApplyThread` не зовёт `FindThreadSite`. Значит, в сценарии тестера
  упал, вероятно, другой элемент того же перестроения — нужен его файл/лог.
- Проверить на Windows (после слияния и новой сборки): три сценария — сопряжение слишком
  большим радиусом; резьба, закрыть панель без грани; выдавливание «до грани» тела вращения.
  Ожидается: не вылет, а ошибка операции в дереве.
- 2026-10-12, Windows (сборка CI из PR #5, `1fe8086`), проверил Миша: вылетов нет ни в одном
  сценарии. Сопряжение и резьба проходят без ошибок. Выдавливание «до грани» с целью на
  криволинейной грани тела вращения не строится (ошибка операции, программа живёт) — это
  уже не вылет, а недоработка операции: следующий шаг п.2 — почему OCCT не строит
  выдавливание до кривой грани (`Extrema_ExtCC` / `BRepClass3d_SolidClassifier`, HANDOFF §6а).
- 2026-10-12, п.2, выдавливание «до» кривой грани — `8e07362`. OCCT в контейнер через apt не ставится
  (прокси), но GitHub открыт: OCCT 7.9.3 (та же версия, что в MSYS2 — 7.9.3-3) собран из исходников
  в `/opt/occt` (~1 ч на 2 ядрах, без Draw/OpenGL; тулкиты — только нужные проекту). Сборка проекта:
  `cmake --preset linux-debug -DBZ_BUILD_APP=OFF -DOpenCASCADE_DIR=/opt/occt/lib/cmake/opencascade`,
  тесты — `LD_LIBRARY_PATH=/opt/occt/lib`. Если контейнер новый — собирать заново.
- Найдено и исправлено: шов тела вращения лежит в плоскости его эскиза. Точка грани на шве →
  `BRepExtrema` даёт «на ребре» → `NormalAt` брал нормаль середины грани (дальняя сторона вала) →
  `ResolveAnyFace` отбрасывал грань («Грань «до» не найдена»), а у трубки брал внутреннюю грань
  и строил столбик не той высоты. Теперь нормаль — в самой точке через p-кривую ребра.
  Тест `tests/kernel/ExtrudeToFaceTests.cpp`: вал, трубка, конус, тор, сфера — на шве и вне его.
- Чего не воспроизвести на Linux: сбоя OCCT. Вне шва все кривые грани (цилиндр, конус, тор, сфера)
  строятся с верным объёмом. При выборе в приложении нормаль и точка берутся тем же `NormalAt`,
  поэтому щелчок по шву там, вероятно, проходил и раньше — **исправление может не совпасть с тем,
  что видел Миша.** Если на Windows ошибка в дереве — «Геометрическое ядро не смогло выполнить
  операцию (сбой внутри OpenCASCADE)», это пойманный сбой из HANDOFF §6а (только Windows, тот же
  OCCT 7.9.3 — вероятно, сборка MSYS2/GCC 16, как с `std::format` в `ddb429a`). Нужны: точный текст
  ошибки, строка лога `OCCT fault (…)` и файл .bzc.
- Варианты подхода, если сбой — в нашем `BRepClass3d_SolidClassifier` из `CutToFace`
  (src/kernel/occt/Extrude.cpp): (а) не классифицировать куски точками, а оставлять те, что
  касаются плоскости эскиза (у них есть плоская грань в этой плоскости) — без классификатора;
  (б) история `BRepAlgoAPI_Splitter`: куски, куда перешли начальные грани призмы
  (`MakePrism::FirstShape`); (в) родная операция OCCT `BRepFeat_MakePrism` с `Perform(Until)`.
  Но классификатор зовут и сами булевы операции (`IntTools_Context`), так что без адреса сбоя
  из Windows-лога (pefile по экспортам DLL, HANDOFF §6а) выбор между ними — гадание.

расчёта» — похоже на причину). Тест: эскиз → выдавливание → Undo → тела нет сразу.

**Б3 — сечение остаётся после «Отмена».** `src/app/features/SectionEditor.cpp`,
`src/app/viewport/Section.cpp`, `src/document/SectionFeature.*`. Проверить: отмена убирает
временную операцию/предпросмотр, подтверждение — один шаг истории, Undo после него
возвращает как было. Если причина в общем механизме панелей (`OperationEditor.h`) —
проверить ещё 2–3 панели на том же сценарии (начать → Esc).

**Заметки:**
- 2026-10-12, Б2 и Б3 — `5963bd7`. Одна причина: убрать **последнюю** операцию (отмена её

  операций было при последней сборке. Б3 закрыт этим же (общий механизм панелей), отдельный
  инструмент «Сечение» вида (полоска сверху) убирается своей кнопкой — его не трогал.

## Новые баги от Миши (2026-10-12)

- Окружность «уезжает» при изменении размера — `889195e`. Первый размер эскиза масштабирует весь
  эскиз (чтобы сохранить пропорции), и делал это относительно начала координат эскиза — центр
