# Как помочь BreezeCAD

Спасибо, что хотите помочь! Проект открыт для контрибьюторов.

Прежде чем начать — прочитайте:
- `docs/HANDOFF.md` — общая картина проекта.
- `docs/RULES.md` — 38 правил работы (обязательны).
- `docs/ARCHITECTURE.md` — слои и структура кода.
- `docs/CANON_FEATURES.md` — что должно быть.

---

## Что приветствуется

- Исправление багов (см. `docs/TECH_DEBT.md`, `docs/UI_ISSUES.md`).
- Документация.
- Тесты для ядра.
- Иконки в стиле Lucide (SVG, 24x24, stroke 2).
- Переводы (когда закроем MVP).
- Оптимизация под слабое железо.

---

## Что НЕ приветствуется

- Добавление функций, которых нет в каноне без обсуждения.
- Изменение формата `.bzc` без ADR.
- Прямой доступ к OCCT вне `src/kernel/`.
- Хардкод путей, цветов, размеров.
- Файлы >500 строк.
- Монолитные PR (один PR = одна задача).

---

## Перед началом работы

1. **Открыть issue** с описанием проблемы или предложения.
2. **Дождаться обсуждения** (если задача нетривиальная).
3. **Форкнуть** репозиторий.
4. **Создать ветку** с понятным именем:
   - `feat/hole-operation`
   - `fix/ribbon-topology`
   - `docs/architecture-update`

---

## Требования к коду

### Стиль

- C++17.
- `clang-format` (файл `.clang-format` в корне).
- Классы — PascalCase.
- Функции — camelCase.
- Приватные поля — `my` + PascalCase (`myWindow`).
- Константы — `k` + PascalCase (`kMaxUndoSteps`).
- `#pragma once` в заголовках.
- Forward declarations где можно.

### Слои (не нарушать)

    ui/        ImGui, ribbon, панели, диалоги
    app/       Application, CommandStack
    doc/       BreezeDocument, DocumentData
    kernel/    IKernel, OcctKernel
    platform/  GlfwWindow, FileDialog

UI не знает про OCCT. Ядро не знает про ImGui. Между ними — IKernel.

### Правки файлов

- Использовать UTF-8.
- Сохранять CRLF (не конвертировать в LF).
- Кириллица в коде — только в комментариях и UI-строках.

### Коммиты

Формат: `<тип>(<область>): <краткое описание>`

Типы: `feat`, `fix`, `refactor`, `docs`, `build`, `chore`, `assets`,
`wip`.

Примеры:
- `feat(kernel): add Hole operation to IKernel`
- `fix(ui): ribbon buttons no longer truncated`
- `docs: update CANON_FEATURES with STL viewer`

## Процесс

1. Форк.
2. Ветка.
3. Изменения.
4. **Сборка** — обязательно проверить, что проект собирается.
5. **Запуск** — проверить, что приложение работает.
6. **Тесты** — если есть, прогнать.
7. Коммит (один на логическую часть).
8. Push в свой форк.
9. **Pull Request** в `main` с описанием:
   - Что изменено.
   - Зачем.
   - Как проверено (команды, скриншоты).

---

## Проверка перед PR

Чек-лист:

- [ ] Проект собирается (`ninja`).
- [ ] Приложение запускается (`./run.sh`).
- [ ] Не сломаны существующие функции.
- [ ] Нет warnings от моего кода.
- [ ] Коммиты с понятными сообщениями.
- [ ] Обновлена документация (если применимо).
- [ ] Если UI — есть скриншот.

---

## Обновление документации

Если ваш PR меняет:

- **Функционал** — обновить `docs/CANON_FEATURES.md`.
- **UI** — обновить `docs/UI_LAYOUT.md` и `docs/BUTTONS_INVENTORY.md`.
- **Архитектуру** — новый ADR в `docs/ADR/`.
- **Закрыт баг** — перенести в `docs/TECH_DEBT.md` или `docs/UI_ISSUES.md`.
- **Что-то значимое** — добавить в `docs/CHANGELOG_WORK.md`.
