# Как помочь BreezeCAD

Спасибо, что хотите помочь! Проект открыт для контрибьюторов.

Прежде чем начать — прочитайте:
- `docs/ARCHITECTURE.md` — модули, поток данных, рецепты «как добавить
  инструмент эскиза / операцию / настройку». **Начинать отсюда.**
- `docs/RULES.md` — правила работы (обязательны).
- `docs/dev/HANDOFF.md` — текущее состояние, план, известные ограничения.
- `docs/dev/WORKLOG.md` — журнал решений: почему сделано так, какие ловушки
  OCCT уже найдены.
- `docs/ADR/` — архитектурные решения.

---

## Что приветствуется

- Исправление багов (см. «Известные ограничения» в `docs/dev/HANDOFF.md`).
- Документация.
- Тесты для ядра (`tests/`).
- Иконки в стиле проекта (SVG 32×32, линия #1D4ED8, вспомогательные #6F7884,
  акцент #E5484D; лежат в `assets/icons`).
- Переводы (`translations/README.md`).
- Оптимизация под слабое железо.

---

## Что НЕ приветствуется

- Добавление функций без обсуждения.
- Изменение формата `.bzc` без ADR (новые поля — только с чтением по
  умолчанию, старые файлы должны открываться).
- OCCT вне `src/kernel/` и `src/render/`; ImGui вне `src/ui/` и `src/app/`.
- Хардкод путей; цвета — только из токенов темы.
- Видимый текст без `Tr()` / `Trf()`.
- Монолитные PR (один PR = одна задача).

---

## Перед началом работы

1. **Открыть issue** с описанием проблемы или предложения.
2. **Дождаться обсуждения** (если задача нетривиальная).
3. **Форкнуть** репозиторий.
4. **Создать ветку** от `next` с понятным именем:
   - `feat/thread-operation`
   - `fix/ribbon-topology`
   - `docs/architecture-update`

## Требования к коду

### Стиль

- C++20; отступ 4 пробела, строка до ~130 знаков (как в существующем коде).
- Типы и функции — PascalCase (`Model::Rebuild`, `FindThreadSite`).
- Локальные переменные и поля структур — camelCase.
- Приватные поля классов — `my` + PascalCase (`myViewport`).
- Константы — `k` + PascalCase (`kMaxUndoSteps`).
- `#pragma once` в заголовках; в начале заголовка — 1–3 строки, что это.
- Идентификаторы и комментарии к коду — по-английски; русский — только
  в строках интерфейса (это ключи перевода).
- Комментарий объясняет «зачем», а не «что»: ловушки OCCT, неочевидные
  решения, единицы измерения (`mm`, `rad`).

### Модули (зависимости только вниз)

    core      математика, единицы, выражения, лог, перевод
    sketch    2D-эскиз и решатель            (без OCCT и ImGui)
    document  дерево операций, файл .bzc     (без OCCT и ImGui)
    kernel    перестроение модели на OCCT    (без ImGui)
    render    вьюпорт OCCT/OpenGL
    ui        тема, шрифты, виджеты ImGui
    platform  окна, пути, диалоги
    app       лента, панели, редакторы

Подробно — `docs/ARCHITECTURE.md`.

### Файлы

- UTF-8, переводы строк LF.
- Новая логика в `sketch`/`document`/`kernel` — с тестом в `tests/`.

### Коммиты

Заголовок: `<тип>: <что изменилось, для человека>` — по-английски, до ~72 знаков.
Типы: `feat`, `fix`, `refactor`, `perf`, `test`, `docs`, `build`, `ci`, `chore`.

Тело (обязательно, кроме мелочей вроде опечаток) — коротко по пунктам:

    What:   что умеет программа / что исправлено (как видит пользователь)
    Why:    зачем; для fix — причина бага, а не только симптом
    Where:  ключевые файлы и функции, с которых начинать чтение
    Tested: какие тесты добавлены, что проверено вручную

Пример — коммит `c0bfa3d` (`git show c0bfa3d`).
Один коммит — одна логическая часть: попутные исправления отдельно.

## Процесс

1. Форк.
2. Ветка.
3. Изменения.
4. **Сборка** — обязательно проверить, что проект собирается.
5. **Запуск** — проверить, что приложение работает.
6. **Тесты** — если есть, прогнать.
7. Коммит (один на логическую часть).
8. Push в свой форк.
9. **Pull Request** в `next` с описанием:
   - Что изменено.
   - Зачем.
   - Как проверено (команды, скриншоты).

---

## Проверка перед PR

Чек-лист:

- [ ] Собирается без предупреждений:
      `cmake --preset linux-debug && cmake --build --preset linux-debug`
      (Windows — MSYS2/MinGW64, см. `.github/workflows/build.yml`).
- [ ] Тесты проходят: `ctest --preset linux-debug`.
- [ ] Приложение запускается, изменённое проверено руками.
- [ ] Новые строки интерфейса — в `Tr()`; `python3 scripts/i18n/extract.py`.
- [ ] Коммиты с телом What/Why/Where/Tested.
- [ ] Если UI — есть скриншот.

## Обновление документации

Если ваш PR меняет:

- **Модули, поток данных, способ добавления чего-либо** — `docs/ARCHITECTURE.md`.
- **Архитектурное решение** — новый ADR в `docs/ADR/`.
- **Состояние/план/ограничения** — `docs/dev/HANDOFF.md`.
- **Что-то значимое или найдена ловушка** — запись в `docs/dev/WORKLOG.md`.
